# CLAUDE.md — Telemetry Web

**This file is a briefing for an AI assistant.** Read it before touching any code in this folder.

## What This Project Is

The always-on public dashboard for Greenpower telemetry. A small Node/Express app meant to run on Railway 24/7, reachable at whatever domain is pointed at it (see the GoDaddy DNS notes below). It does **not** talk to the ESP32 receiver directly — [`receiver_agent`](../receiver_agent/CLAUDE.md) does that, and POSTs live packets here whenever it's actively forwarding. Live data still flows through an in-memory value the same as before; as of this pass, every packet is **also** persisted to Postgres and grouped into automatically-bounded "sessions" so past drives/tests can be browsed and exported later, not just watched live.

The three-part system: `greenpower_receiver` (ESP32, LoRa → USB serial) → `receiver_agent` (runs on whatever computer the receiver is plugged into, watches for it, asks the user before forwarding) → `telemetry_web` (this folder, always-on public site).

## Rules and Constraints

### Live status is still in-memory only — persistence is a separate, parallel path
`latest`/`lastUpdateMs` in `server.js` are still plain in-memory variables, cleared on every restart/redeploy, and that's still correct for "is the car live right now." Don't try to derive `/api/latest` from the database — it's deliberately a separate, cheap, always-current path that doesn't depend on Postgres being configured or reachable.

### Database is optional — `pool` being `null` must never crash a request
`server.js` only creates the `pg` `Pool` if `DATABASE_URL` is set (Railway injects this automatically once a Postgres plugin is attached — see README.md's setup section). Every DB-touching route (`recordPoint()`, `/api/sessions`, `/api/sessions/:id/points`, `/api/sessions/:id/export.csv`) checks `if (!pool)` first and degrades gracefully (silent skip for recording, `503` for the read endpoints) rather than throwing. Keep that guard on any new DB-touching code — local dev without a configured Postgres, and any deploy where the plugin hasn't been added yet, both depend on this not crashing.

### Telemetry is stored as JSONB, not one column per field — this is deliberate
`telemetry_points.data` is a single `JSONB` column holding the whole packet, not `speed_mph FLOAT, batt_volt FLOAT, ...`. `telemetry_packet_t` has changed shape twice already in this project's history (ESC fields added, RPM fields reworked) — a fixed relational schema would need a migration every time that happens again. JSONB means the DB layer doesn't care what fields exist. The one place a fixed field list *does* exist is `CSV_COLUMNS` in `server.js`, and that's intentional — see below.

### `CSV_COLUMNS` is a fixed, hand-maintained list — keep it in sync with the packet shape
CSV export doesn't derive its columns from whatever keys happen to be in any one row (which would make column order unstable, or silently drop columns missing from row 1). It uses the explicit `CSV_COLUMNS` array in `server.js`. If a field is added to `telemetry_packet_t` (and to `METRICS` in `index.html` per the rule below), add it to `CSV_COLUMNS` too, in the same change — otherwise it'll flow into the database fine but silently never appear in an exported CSV.

### Sessions are bounded by a time gap, not an explicit start/stop signal
`SESSION_GAP_MS` (60000) in `server.js`: a new session starts whenever a packet arrives and either no session is active yet, or the gap since the last recorded packet exceeds this. Nothing in the firmware, `receiver_agent`, or the dashboard explicitly signals "session started" or "session ended" — this is purely inferred from the data flow itself. A receiver briefly losing LoRa sync for under a minute stays in the same session; walking away for an hour and coming back starts a new one. If a different session-boundary policy is ever wanted (explicit start/stop button, vehicle-ignition signal, etc.), that's a real design change to discuss, not a constant to tweak blindly.

### Session views are one-shot renders, not live — don't wire them into the live poll loop
`viewSession()` in `index.html` fetches a session's full point history once and builds Chart.js charts from the complete static array. This is architecturally different from the live Overview/dedicated-tab charts, which grow incrementally via `pushHistory()` on every live poll tick. Don't merge these two code paths — a past session's data doesn't change, and re-polling it repeatedly would be pure waste.

### `POST /api/telemetry` requires the API key; `GET /api/latest` does not
The write endpoint is authenticated (`Authorization: Bearer <TELEMETRY_API_KEY>`) so random internet traffic can't inject fake telemetry. The read endpoint is deliberately public with no auth — it's what the dashboard itself polls, and there's nothing sensitive in a speed/RPM/voltage reading. Don't add auth to `/api/latest`, and don't remove it from `/api/telemetry`.

### `TELEMETRY_API_KEY` must be set as a real Railway environment variable
Without it, `server.js` generates a random key at boot and only prints it to the server log — useless for `receiver_agent` running on someone's laptop, since it has no way to read Railway's log. Set `TELEMETRY_API_KEY` in Railway's dashboard (Variables tab) to a real fixed value, and put the same value in `receiver_agent`'s config. If the key is ever rotated, both sides need updating together.

### `STALE_MS` (2000) defines "offline"
If no POST arrives within this window, `/api/latest` reports `online: false` and the dashboard shows the offline banner, even though `data` still holds the last-known values. The frontend intentionally still displays those stale numbers (not blanked out) alongside the offline indicator — don't change that without a reason, it's useful to see the last known state.

### Dashboard is a single static file, no build step
`public/index.html` is plain HTML/CSS/JS, served directly by `express.static`. Don't introduce a bundler/framework for this unless the UI genuinely outgrows a single file — it deploys as-is with zero build configuration, which matters for how simply this deploys to Railway.

### Live chart history (Overview/dedicated tabs/Multi) is still browser-only and short — that's separate from Sessions
The rolling `history`/`historyTimes` arrays (`MAX_POINTS = 150`, ~30s at 5 Hz) that feed the *live* charts are still client-side-only and still reset on page load — this didn't change. What changed is that there's now a **separate, independent, server-side** long-term record (Postgres) reachable through the Sessions tab, not by extending `MAX_POINTS` or feeding the live charts from the database. Don't conflate the two: the live charts are deliberately cheap and ephemeral; Sessions is deliberately durable and fetched on demand.

### Every chart's x-axis is real wall-clock time — server-stamped, not client-guessed
This was a real bug, fixed in this pass: the live charts used to plot against `historyIndex`, a plain incrementing integer (`pointCount++`) with the x-axis hidden entirely on the mini-charts — not a timestamp at all, on any of them. Two things now make it real time:
1. `server.js` stamps `received_at` (its own `Date.now()`, server receive time) onto the `latest` object in the `POST /api/telemetry` handler — this is intentionally NOT the same value passed to `recordPoint()`/stored in the DB, which gets its own `received_at` from Postgres's `now()` at insert time. Two independent timestamps, two independent purposes (live display vs. durable record) — don't try to unify them into one.
2. The frontend's `historyTimes` array stores that real `d.received_at` (epoch ms), and `applyHistory()` formats it to a locale time string once per update for every chart's labels — mini-charts included, via `BASE_OPTS.scales.x` now defaulting to `display:true` instead of `false`.

If a chart's x-axis ever looks like it's showing sequence numbers or is missing again, check that the data source is actually populating `received_at` — don't quietly reintroduce a counter as a stand-in.

### History points are deduped by `seq`, not by poll tick
`poll()` only calls `pushHistory()`/`pushRawLine()` when `data.seq` differs from the last seen value. This matters because the dashboard polls at the same 5 Hz rate the sender transmits at — without the dedupe check, a single momentarily-slow poll response or a dropped LoRa packet would cause the same packet to be re-fetched and plotted as if it were a new sample, flattening the chart at that point instead of correctly showing a gap. Don't remove this check to "simplify" the polling loop.

### `METRICS` is the single source of truth for every telemetry field shown
Adding a new field to `telemetry_packet_t` that should appear on the dashboard means adding one entry to the `METRICS` object in `index.html` (label, unit, color, decimals, normalization range for the Multi tab, and whether it's on by default there) — the overview mini-charts, dedicated per-metric chart pages, stat cards, and Multi-tab toggle buttons are all generated from that one object, not hand-duplicated per field. Don't add a new metric's markup by copy-pasting an existing tab's HTML; add it to `METRICS` and (if it needs its own tab rather than just showing in Overview/Multi) add the tab markup referencing the same field key so the existing JS wiring picks it up automatically (`ov-<key>`, `big-<key>`, `chart-<key>`, `ovchart-<key>` id conventions). **Also add it to `CSV_COLUMNS` in `server.js`** (see the Sessions rules below) — `METRICS` and `CSV_COLUMNS` are two independent lists that both need updating for a new field to be fully wired end-to-end (dashboard display AND CSV export); a field only in one of them will display but not export, or export but not display.

### GPS/IMU/ESC validity comes from `flags`, not from checking for non-zero values
`gpsValid()`/`imuValid()`/`escValid()` read bit 0 / bit 1 / bit 3 of the packet's `flags` byte (matching `PKT_FLAG_GPS_VALID`/`PKT_FLAG_IMU_VALID`/`PKT_FLAG_ESC_VALID` in the firmware's `config.h` — note bit 2 / `0x04` is the current-sensor flag, not ESC, easy to mix up) rather than guessing validity from whether `latitude`/`roll_deg`/`esc_setpoint_pct` etc. happen to be zero — a real reading can legitimately be zero (e.g. sitting still at a roll of exactly 0°, or the ESC's setpoint genuinely at 0%), so a zero-check would misreport a valid reading as invalid. Only push a GPS point onto the raceline trail when `gpsValid()` is true.

### Onboarding / access gate — required password, then a platform-specific optional install step, then a feature overview, then a Settings tour
`#onboarding-overlay` (`z-index:200`, above literally everything else including the required-update banner's 60 AND — see the confirm-modal z-index note below — everything except a confirm-modal opened from within it) shows on first visit, both desktop and mobile, before any dashboard content is usable. Steps, in order: **password** (both platforms — a plain-text comparison against `ONBOARDING_PASSWORD`, `'SentinelRacing26!'`, hardcoded client-side; see the note below on what that does and doesn't mean security-wise) → **install** (mobile only) *or* **agent** (desktop only) — `onboardingSteps` is `IS_MOBILE ? ['password','install','overview','settings'] : ['password','overview','agent','settings']`, so each platform gets exactly one relevant, NOT required, skippable companion-install step, in a different position in the sequence (mobile promotes installing the app itself right after the password; desktop shows the general feature overview first, THEN offers the receiver agent, since agent installation only matters to someone actually running a receiver — see the "agent" step's own note) → **overview** (both — a short list of feature bullets) → **settings** (both, the final step — either "Open Settings" (finishes onboarding AND switches straight to the Settings tab) or "Skip — Go to Dashboard" (finishes onboarding, leaves whichever page was already active)). `ONBOARDING_KEY` (`gp_onboarding_v1_complete`) is checked once at load; if unset, the overlay shows and the step index starts at 0.
**Step switching is animation-based, not a display↔opacity crossfade** — `.onboarding-step-active` (added to exactly one step at a time by `showOnboardingStep()`) both sets `display:flex` AND carries a one-shot `@keyframes` entrance animation (`onboardingStepIn`); a `display:none`→something toggle has no valid "before" state for a `transition` to animate from (the same documented gotcha `.mobile-navsheet` ran into elsewhere in this file), but a CSS *animation* has no such requirement — it just starts playing the instant the element enters the render tree with the class already on it. Simpler and safer than a real crossfade for an access-gate flow regardless: JS only ever marks ONE step active, so there's no risk of two steps overlapping mid-transition or a "stuck between steps" state. The overview step's feature bullets are individually staggered (`nth-child` animation-delay) for a bit of extra polish. Primary "move forward" buttons (`.onboarding-btn-primary`) use the same solid accent gradient (`linear-gradient(135deg, var(--accent), var(--accent2))`) install-fab/active tabs already use elsewhere, not the outlined `.btn-accent` style — this is the one recurring "important, colorful" action on every step.
**The desktop "agent" step opens the REAL `#download-confirm-modal`** (`showDownloadConfirm()`, the same function the header's Download Agent button calls) rather than duplicating that flow — which is why `.confirm-modal`/`.confirm-modal-backdrop`'s z-index had to move from 30/31 to 210/211, above `.onboarding-overlay`'s 200: a confirm-modal opened from within onboarding needs to render on TOP of it, not disappear behind it. **Both halves of that pair must move together** — a real bug hit while building this: bumping only the backdrop's z-index above the modal's own (unchanged) 31 made the backdrop itself intercept clicks meant for the modal's buttons (verified via `elementFromPoint` landing on the backdrop, not the Download button) — confirmed and fixed before shipping, both now at 210/211. An actual click-through on `#download-confirm-go` while the "agent" step is active also auto-advances onboarding (a listener added alongside the modal's own existing `hideDownloadConfirm` one, not replacing it) — canceling out of the modal instead leaves the user back on the "agent" step, where its own separate Skip button still works.
**This is a UI speed-bump, not real access control** — the password check happens entirely in client-side JS against a hardcoded string anyone can read directly from this file's source (view-source, or just grep it), and every actual API endpoint (`/api/latest`, `/api/sessions`, etc.) remains exactly as public/unauthenticated as it already was (see the `/api/latest` auth rule elsewhere in this file — `POST /api/telemetry` is the only endpoint with real auth, via `TELEMETRY_API_KEY`, and that's unrelated to this gate). Don't describe this to a user as "securing" the dashboard's data — it only gates the dashboard's own UI from a casual visitor, nothing more. If real access control is ever wanted, that's a server-side auth mechanism to design, not a JS string comparison.
**The install step mirrors, but deliberately doesn't share code with, the existing `install-fab`/`checkIosInstallHint()` logic** (same three cases: real `beforeinstallprompt` captured in `deferredInstallPrompt`, iOS with no such API — Share-sheet instructions instead — or already running standalone) — the two UIs (a floating popover vs. a full-screen onboarding step) render differently enough that sharing the DOM-manipulation code wasn't worth the coupling; the underlying `deferredInstallPrompt` variable and `hideInstallUi()` function ARE reused directly, though, since those are the actual install-triggering plumbing, not UI.
**"Clear all cookies for this update" was handled two ways**, not one: (1) `ONBOARDING_KEY` is a brand-new name, never used by any earlier version of this file — that alone guarantees every existing visitor (not just genuinely new ones) sees the new gate on their next visit, since nobody has this key set to `'1'` yet; (2) a one-time migration (`localStorage['gp_cookies_cleared_v1']`, checked/set once) additionally clears any real browser cookies, purely defensive since this app has never actually set one itself (everything else here is `localStorage`) — the request was specifically about cookies, so this doesn't also wipe other already-saved preferences (range/haptics/overview-cols etc.) for returning users the way the Settings button below deliberately does.
**Settings → Clear Website Data** (`clearAllWebsiteData()`, behind its own `#clear-data-confirm-modal` — reuses the same `.confirm-modal` markup/CSS as the download-agent and exit-app confirmations, a third independent instance of the same pattern) is the ongoing, user-facing, MUCH more thorough version: `localStorage.clear()` + `sessionStorage.clear()` + clears any real cookies + unregisters any service worker + deletes any Cache Storage entries, then `location.reload()`. This wipes `ONBOARDING_KEY` along with everything else, so a reload after clearing correctly shows the onboarding gate again — that's intentional, not a side effect to guard against.

### Exit confirmation on Android back gesture — `window.history`, never bare `history`
This is a single-page app with no real navigation (tabs are pure JS class-toggling, no URL/hash changes ever happen), so a plain page load leaves only ONE entry in the browser's history stack — on an installed Android WebAPK, a back gesture/button press from there has nothing to go back TO, so Android just closes the app outright with no chance to intercept it. Fixed with the standard "confirm before exit" PWA pattern: `window.history.pushState({gpExitGuard:true}, '')` seeds one spare entry on load, and every `popstate` (fired the instant a back gesture consumes that entry) immediately re-pushes a fresh replacement AND shows `#exit-confirm-modal` (reuses the exact `.confirm-modal`/`.confirm-modal-backdrop` markup/CSS the download-agent confirmation already uses — no reason to build a second visual language for a second yes/no dialog) instead of letting the gesture fall through to a real exit. The guard-entry count never actually drops, so the user can't swipe past it without going through the dialog. On confirm, `awaitingExit=true` skips the re-push/re-show so a `window.history.go(-2)` (undo the just-consumed guard AND the original real entry, in one shot) is free to actually exit — nothing left to intercept it.
**A real bug, caught before shipping, not a style nit**: this script already has a top-level `const history = {}` (the live-chart data buffer — see `MAX_POINTS`/growing-buffer rules elsewhere in this file) declared LATER in the same script. A bare `history.pushState(...)` reference textually BEFORE that `const` still resolves to that same script-scoped binding (not the global `History` object) due to how `const`/`let` hoisting works — and since it's accessed before its own initializer runs, it throws `ReferenceError: Cannot access 'history' before initialization` **and this halts the ENTIRE rest of the script's execution**, silently breaking everything below it (polling, chart rendering, every other feature) on every single page load. Caught via `read_console_messages` before this reached the user — every reference to the real browser History API in this file MUST use `window.history`, never bare `history`. If a future edit ever needs the real History API here, check for this shadowing first.

### Overview Boxes to Show has a "can't deselect the last one" guard, and a non-obvious default set
The `change` handler on each checkbox in `#settings-ov-mobile-list` refuses (snaps the checkbox back to checked, doesn't save/apply) if unchecking it would leave zero visible mobile-Overview tiles — an empty Overview page with nothing left to tap would have no visible way back to turning any back on. Separately, `OV_MOBILE_DEFAULT_ON` (a `Set`) defines which of the 13 items start ON before any `localStorage` override exists: **Speed, Battery, Motor Volt, Current, Temp, Motor RPM, Wheel RPM, Packet #** (8 total) — Roll/Pitch/Yaw/GPS/Link start OFF. This was an explicit request, not a guess at "sensible defaults" — don't reorder/change this set without being asked again.

### App update check — `/api/version` (server) + `checkAppVersion()` (client) — REQUIRED, not dismissible
`server.js` computes a SHA-1 hash of the served `public/index.html`'s content once at boot (`APP_VERSION`) and exposes it via `GET /api/version` (public, no auth — same reasoning as `/api/latest`). Deliberately a computed hash, not a hand-maintained version string — nothing to remember to bump, and it changes if and only if the page actually did on a real deploy. The client's `checkAppVersion()` fetches this with `cache:'no-store'`, treats the FIRST successful fetch as the baseline (`appVersion = d.version`, no banner), and calls `showUpdateRequired()` the moment a later fetch returns a different hash. Runs once on load, every 5 minutes via `setInterval`, and again on `visibilitychange` back to `'visible'` — that last one matters most in practice, since an installed PWA sitting backgrounded for hours (missing a deploy entirely on the timer) is the actual scenario this exists for, more than someone leaving a browser tab open and staring at it.
**`#update-banner` has no dismiss button, and `#update-banner-backdrop` blocks interaction with the rest of the page while it's showing** — per explicit request, this is required, not a light notice. The backdrop is `position:fixed; inset:0; z-index:59` (just under the banner's own `z-index:60`, but above the mobile nav bar/sheet's 14/15 and everything else) so it genuinely intercepts clicks/taps on anything behind it, not just visually dims it — verified via `document.elementFromPoint()` (real hit-testing) landing on the backdrop at a tab's coordinates, not the tab itself; a plain `.click()` call in a test is NOT a valid way to verify this, since programmatic `.click()` bypasses hit-testing/z-index entirely and fires regardless of what's visually on top. `#update-banner-reload` (still hittable — it sits above the backdrop) just calls `location.reload()` — no service worker to bypass, since `sw.js` never caches anyway (see its own rule), so a plain reload always gets the current file. If this ever needs to become dismissible again, that's a real behavior change to confirm, not a default to fall back into.

### Orientation lock is three layers, only one of which is airtight
A website fundamentally can't override the phone's OS-level auto-rotate setting from JS alone — this was a real ask ("prevent the user from rotating their phone screen"), and the honest answer is "reach for every real lever, but only one of them is guaranteed." (1) `manifest.json`'s `"orientation":"portrait-primary"` (was `"any"`) is the actual, reliable lock — but ONLY for an installed PWA/WebAPK launched in standalone display mode, and even then only on a *fresh* install (an already-installed copy needs uninstall+reinstall, same manifest-caching limitation as the app-name/theme-color fixes noted elsewhere in this file). (2) `screen.orientation.lock('portrait')` (mobile-only, wrapped in try/catch, silently no-ops on failure) is a second attempt aimed at that same standalone case — most browsers reject it outside Fullscreen mode, which this page doesn't use, so treat this as a bonus, not something to rely on. (3) `.landscape-lock-overlay` is the only layer that reaches EVERY remaining case (a plain, not-installed mobile browser tab, or an already-installed copy that hasn't been reinstalled yet) — pure CSS, `@media (max-width:860px) and (orientation:landscape)`, no JS involved so it can't silently fail: a full-screen "rotate back to portrait" message, since none of this file's mobile-specific layout was ever designed to support landscape.

### `#gps-map` needs `isolation:isolate` or Leaflet paints over the mobile toolbar
Real bug, not a Leaflet misconfiguration: Leaflet's internal panes (tile/overlay/shadow/marker/popup) use `z-index` values up to ~700, and `.leaflet-container` doesn't establish its own stacking context by default. Without `isolation:isolate` on `#gps-map`, those high `z-index` panes compete directly in the PAGE's root stacking context against other fixed-position UI — specifically `.mobile-navbar` (`z-index:15`) — and win, painting the map on top of the toolbar despite being much earlier in the DOM and visually "behind" it in every other sense. `isolation:isolate` confines every Leaflet `z-index`, however high, inside `#gps-map`'s own stacking context — only `#gps-map`'s own position in the page's stacking order matters to anything outside it after that. If a future map/widget embed shows the same "floats over fixed UI it shouldn't" symptom, this is the first thing to check — it's almost always a missing stacking-context boundary, not a z-index number that needs to go higher.

### The raceline map auto-zooms to fit the recorded trail, not just a fixed-zoom follow
`updateGpsMap()` used to always either `setView(..., 17)` (first fix) or `panTo()` (every fix after, same zoom forever) — the car could easily wander outside a fixed zoom-17 view with no automatic way back to seeing the whole route short of a manual zoom-out. Now: on every fix after the first, if the new point falls outside the map's current visible bounds (`!gpsMap.getBounds().contains([lat,lon])`), it calls `gpsMap.fitBounds(gpsPolyline.getBounds(), GPS_FIT_OPTS)` instead of `panTo()` — this re-zooms/pans to fit the WHOLE trail collected so far, not just the new point, so the map keeps the full route visible as it grows rather than cropping to wherever the car currently is. Points still inside the current view just `panTo()` as before (no unnecessary re-zoom while nothing's actually left the frame — a user who's manually zoomed in to inspect part of the trail doesn't get yanked back out every 200ms for a point that's still on screen). `GPS_FIT_OPTS` (`padding:[30,30]`, `maxZoom:19`) is shared with the tab-switch handler, which was also changed to `fitBounds()` the whole trail (when there are 2+ points) instead of just re-centering on the last known point at whatever zoom the map happened to have — arriving on the Raceline tab now shows the full route at a glance. Leaflet's `fitBounds()` picks the largest whole zoom LEVEL that fits the padded bounds, so the literal requested bounds can end up a few percent outside the final viewport at some zoom steps (normal Leaflet quantization, not a bug) — the visible zoom/pan direction is still always correct.

### ESC mode/state are strings, not `METRICS` entries
`esc_mode`/`esc_state` are handled by hand in `applyState()` (the `esc-mode`/`esc-state` elements), not added to the `METRICS` registry — `METRICS` assumes every field is a chartable number with decimals and a normalization range, which doesn't apply to a string like `"NORMAL"` or `"RAMP"`. The three numeric ESC fields (`esc_setpoint_pct`/`esc_live_pct`/`esc_ramp_pct`) *are* in `METRICS` and get the full auto-wired treatment (chart, history, Multi-tab toggle) for free. If a future string-valued field needs display, follow the mode/state pattern, not the `METRICS` pattern.

### Colors are CSS custom properties, resolved at chart-creation time
Chart.js needs real color strings, not `var(--foo)` references — `resolveColor()` reads the computed CSS variable once when each chart is built. If the theme's CSS variables are ever changed dynamically (e.g. a light/dark toggle) rather than just at load time, charts built before the change won't pick up new colors without being recreated — this isn't wired up for live theme switching.

### Mobile is a layout mode of the same page, not a separate build
Below `860px` wide, a `@media` block hides the desktop `#tabs` bar and shows `.mobile-sidebar` instead (fixed-position icon rail, `56px` collapsed / `210px` expanded via a `.expanded` class toggle on click), and hides `#overview-right-wrap` (the Overview graph grid) — mobile Overview shows only the stats-bar numbers, never the charts, per an explicit design choice to keep the mobile Overview lightweight. All 12 tabs (`overview`/`speed`/`power`/`temperature`/`rpm`/`esc`/`imu`/`raceline`/`link`/`multi`/`sessions`/`raw`) are duplicated as `.mobile-tab` elements with the same `data-page` values as the desktop `.tab` elements, and the shared click handler keeps both sets' `.active` class in sync — don't add a new tab to only one of the two tab lists, or that page becomes unreachable from whichever UI mode was skipped. Selecting a mobile tab also calls `collapseMobileSidebar()` so the rail snaps back to icon-only after navigating.

### No CSS `transition` on the mobile sidebar's width/label — same reason as the stats-bar collapse
`.mobile-sidebar.expanded` and `.mobile-tab-label` change `width`/`display` instantly, with **no** `transition` property. This mirrors the earlier, deliberate fix to the Overview stats-bar collapse (`.stats-row{display:none}` instead of an animated `max-height`/`grid-template-rows`): CSS-transitioned state changes on this page have repeatedly failed to reliably reach their declared end-state, while instant class-driven toggles have not. If a future edit wants to animate the sidebar, verify the end-state actually applies (computed width, not just class presence) before trusting it — don't re-add a bare `transition:` and assume it works.

### PWA installability — manifest + service worker, deliberately no offline caching
`public/manifest.json`, `public/sw.js`, and the icon SVGs exist solely to satisfy the browser's install criteria (Chrome/Android requires a registered service worker with a `fetch` listener before firing `beforeinstallprompt`). `sw.js` intentionally never calls `event.respondWith()` — this is a live-telemetry dashboard, and caching API responses or the page shell risks silently serving stale readings, which would undermine the entire point of the tool. Install is offered via a small floating button (`#install-fab`), not a banner — see the icon/install rule below. If real offline behavior is ever wanted, that's a deliberate feature to design (e.g. an explicit "stale/offline" state), not something to fall into by adding a cache to `sw.js`.

### Install prompt is a floating icon button, not a banner
`#install-fab` (bottom-right, circular, hidden unless `.show`) replaced an earlier full-width banner — a banner permanently claims header space most visits don't need; the FAB costs nothing until tapped, then opens `#install-popover` (small card, `.show` to display) with the actual "Install" action (Chrome/Android, via the captured `beforeinstallprompt`) or manual instructions (iOS, no such API exists there). Dismissal still persists via the `gp_install_dismissed` localStorage key. **Caught once in testing, worth remembering**: `.install-fab`'s own base rule must never set `display:` itself — the page-wide default-hidden rule (`.mobile-sidebar, .mobile-sidebar-backdrop, .install-fab, .install-popover { display:none; }`) and `.install-fab`'s own base rule are equal-specificity single-class selectors, so whichever is declared later in the stylesheet wins the cascade regardless of the `.show` class; `display:flex` must live only on the `.install-fab.show` rule.

### Icons are inline SVG from one JS map, not emoji
Every static UI icon (nav tabs, header logo, sidebar toggle, hide/customize/refresh/export/close/clear/install buttons) is an empty `<span data-icon="name">` in the HTML, filled in once at load by `applyIcons()` from the `ICONS` map near the top of `<script>` — add a new icon by adding one entry to `ICONS` and one `data-icon="..."` span, not by pasting SVG markup inline. Deliberately not emoji: emoji render inconsistently across platforms/fonts/OSes and read as informal; one hand-authored Feather-style icon set (stroke=`currentColor`, no fill) reads as a coherent design system and automatically inherits whatever text color its container already has. Dynamic runtime status glyphs (e.g. the GPS fix ✅/❌ strings written by `applyState()`) were deliberately left as-is — converting those would mean restructuring the DOM nodes they get written into, and they're data indicators rather than navigation/action iconography.

### Chart axes are pre-filled and range-seeded so a fresh chart doesn't visibly lurch on its first real data points
`history[k]` starts as `MAX_POINTS` nulls (not an empty, growing array) and `historyTimes` is seeded with `MAX_POINTS` backdated placeholder timestamps spaced `SENSOR_INTERVAL_MS_GUESS` (200ms) apart, both filled in before the first `applyHistory()` call (which now also runs once immediately on load, not only after the first live packet). `safeChart()` additionally seeds `scales.y.suggestedMin/suggestedMax` from each metric's `METRICS[k].range` when a `metricKey` is passed. Together this means every chart already shows its full time window and a sane y-range from the very first paint — without it, a brand-new chart auto-fits tightly to whatever 1-2 real points exist so far, and every subsequent point yanks the axes into a new shape until `MAX_POINTS` is finally reached (this was the "graphs expand rapidly when first receiving data" bug). If a new metric/chart is added, pass its `metricKey` through to `safeChart()` — omitting it just means that one chart's y-axis won't get the stabilizing hint, not a hard failure.

### Tooltips work on both hover (desktop) and tap (mobile) — this requires `intersect:false`
Every chart's line has `elements.point.radius:0` (no visible dots — a deliberate look), which means Chart.js's *default* tooltip trigger (`intersect:true`, i.e. "the pointer must land exactly on a rendered point") can never fire — there's no point to land on. `BASE_OPTS` sets `interaction:{mode:'index', intersect:false}` (and each per-chart `options` object needs the same, done in the multi-chart and session-chart config too, since they don't inherit from `BASE_OPTS` directly) so the tooltip instead fires from proximity to an x-position — which is what makes it work as a touch/tap gesture on mobile as well as a mouse hover on desktop, since Chart.js's default `events` list already includes `touchstart`/`touchmove` needing no separate mobile-specific code path. `TOOLTIP_OPTS` is a shared object so all chart types render tooltips with the same dark, theme-matched styling.

### The mobile sidebar uses a real, animated CSS `transition` on `width` — and how to verify that, since the obvious way is broken here
Earlier work concluded CSS transitions in this project "never reach their end state" and switched several UI pieces (the stats-bar collapse, once the mobile sidebar itself) to instant `display`/class-driven toggles instead. Re-investigated during the icon/animation pass: the real cause is specific to the automated browser-preview tool used to verify this page in this dev environment — its browser pane only composites frames (runs `requestAnimationFrame`, applies CSS transitions) while actually displayed/focused; when it isn't, `computer{action:"screenshot"}` fails outright with "the Browser pane is not displayed, so the page is not compositing frames", and under that same condition **any** CSS transition — even a trivial transform on a freshly-created throwaway element — silently never reaches its end state no matter how long you `await`, while forcing `el.style.transition = 'none'` on the same class toggle applies the end state instantly and correctly. That's a property of the verification tool, not of real browsers or of CSS transitions — a normal, visible/focused browser tab always composites and transitions animate normally for real users. **When verifying a CSS transition/animation change in this environment**: don't trust `getBoundingClientRect()`/`getComputedStyle()` read immediately or after an `await setTimeout` — instead temporarily set `el.style.transition = 'none'` before toggling the class, confirm the computed end-state is structurally correct, then remove the inline override; that isolates "is the class/selector/rule correct" (which the tool *can* verify) from "does it animate" (which only a real, visibly-displayed browser can show). Don't strip a `transition` from this file's CSS again based on a synchronous/async-timeout check failing to show the end state — check it this way first.

### Test Mode is a client-side-only fake-data generator, never touches the network
The `#test-mode-btn` toggle in the header runs `genTestPacket()`/`testModeTick()` (near the bottom of `<script>`), which pushes synthetic packets through the *exact same* `applyState()`/`pushHistory()`/`applyHistory()`/`pushRawLine()` functions a real `/api/latest` response would — this is deliberate, so testing the UI can't silently drift from how real data actually renders. It never calls `fetch`/`POST` anywhere, so it can't pollute a real session or write to the database. `poll()`'s own `setInterval` checks `testModeActive` and skips itself while test mode is on, handing back to the real feed the instant it's turned off (an immediate `poll()` call, not waiting for the next 200ms tick).

### `MAX_POINTS` is viewport-dependent, decided once at load — not the same on mobile and desktop
Checked once via `matchMedia('(max-width:860px)')` when the script first runs (60 on mobile vs. 150 on desktop, both still ~the same *time* window at the 5Hz cadence — just fewer points per pixel on a narrower chart). Not re-evaluated on resize/rotation — the `history`/`historyTimes` arrays are pre-sized to this value once (`initHistory`-equivalent code near `STATE / HISTORY`), and there's no live-resize path for them. If a metric/chart needs a different point-density rule later, this is the one place to change it.

### Live charts DO now animate on update — `chart.update()`, not `chart.update('none')`
This reverses an earlier explicit choice ("animation stays OFF for live data updates... looks laggy, not smooth"). `LIVE_ANIMATION` (`{duration:250, easing:'easeOutQuad'}`) is short enough to resolve before the next 200ms tick lands, which is what makes it read as a smooth "line growing" motion instead of the earlier hard per-tick cut, or (if the duration were left longer) visible tween-stacking lag. If update cadence or `LIVE_ANIMATION.duration` ever change together, keep duration comfortably under the tick interval.

### Haptics on chart scrub are attached post-construction, not baked into `BASE_OPTS`
`attachHaptics(opts)` sets `opts.onHover` after `safeChart()`/the multi-chart build their options via `JSON.parse(JSON.stringify(BASE_OPTS))` — functions don't survive a JSON round-trip, so putting `onHover` directly on `BASE_OPTS` would silently vanish on every chart built that way. `navigator.vibrate` is Android-only (silently absent, not an error, on iOS/desktop) and fires once per newly-crossed data-point index while scrubbing, not per pointer-move frame.

### `contextmenu` is blocked at the document level for non-data elements too — CSS alone wasn't enough
A real gap found after the `user-select`/`-webkit-touch-callout` CSS fix (see below) shipped: Android Chrome's "Smart Text Selection" long-press card (the "Search/Share/Copy" popup with its own haptic buzz — colloquially "the Google thing") can still fire on plain non-selectable text regardless of either CSS property, because Chrome forwards long-press coordinates to Android's system text classifier as part of the same gesture pipeline that also drives the desktop `contextmenu` event — it isn't gated by CSS selection state at all. `document.addEventListener('contextmenu', ...)` (near the top of `<script>`, `passive:false` since a passive listener can't call `preventDefault`) calls `preventDefault()` unless the target is inside `COPYABLE_SELECTOR` (the same element list the CSS re-enables selection on, kept as one shared JS constant). This reliably suppresses it everywhere CSS alone didn't, while leaving actual data values (stat readouts, raw log, etc.) untouched.

### Nothing is selectable/copyable except actual telemetry values
`body { user-select:none }` by default, with `user-select:text` re-enabled only on `.stat-value`/`.dedicated-value`/`.stat-unit`/`.dedicated-unit`/`#raw-log`/`#sessions-table td` (and `#esc-mode`/`#esc-state`, which are also `.dedicated-value`). Adding a new numeric/string readout element outside those classes means it won't be copyable unless it's given one of them (or added explicitly) — this was deliberate, not an oversight, if a new display element ever seems to need long-press-to-copy and doesn't have it.
**`-webkit-touch-callout` has to be set alongside `user-select`, not instead of it** — a real gotcha found after the above shipped: iOS Safari's long-press "Copy/Look Up/Share" callout menu is gated by `-webkit-touch-callout`, a *separate* property from `user-select` specifically on iOS — `user-select:none` alone stops the text from visibly highlighting, but iOS still pops that callout menu on a long-press regardless, since the menu there isn't gated by selection state at all. `body` sets `-webkit-touch-callout:none` alongside `user-select:none`, and the same selector list that re-enables `user-select:text` also sets `-webkit-touch-callout:default`. If a future new copyable element is added, it needs both properties re-enabled together, not just `user-select`.

### Mobile dedicated-value pages: even card count → all landscape-rectangle tiles (2/row), odd → last one is a full-width rectangle
Pure CSS, no JS/count-tracking: `.big-row .dedicated-big-card:nth-child(odd):last-child` only matches when the last card's position is itself odd, which is only possible when the row's total count is odd. Pages with a single card (Speed, Temperature) don't use `.big-row` at all and are untouched by this — already a full-width rectangle by default, same as before. Tiles are `aspect-ratio:8/5` (a slight landscape rectangle), not `1/1` — a first pass used true squares, but that took more vertical scroll height than needed; 8/5 keeps the 2-per-row grid while shrinking each tile's height.

### Live charts use a real numeric time x-axis with fixed {x,y} points — NOT Chart.js per-update animation
Two rounds of chasing "the line bugs out"/"graphs don't show up in Test Mode" both traced back to the same earlier mistake: making live charts animate on every `update()` call (`LIVE_ANIMATION`, `chart.update()` instead of `'none'`). That approach is fundamentally wrong for a shifting window of data — Chart.js's animation tweens each ARRAY INDEX's value old→new, but `pushHistory()` shifts the oldest sample out and pushes a new one in every tick, so index 0's "old" value and "new" value belong to two different samples entirely. Every point ends up rippling toward a neighbor's value instead of sliding — the actual cause of "bugs out, isn't smooth." It also caused a second bug: `chart.resize(w,h)` silently no-ops (defers itself) whenever that chart has a Chart.js animation in flight, and a chart fed continuous updates can have "an animation running" almost permanently — so the tab-switch resize fix got silently deferred forever, and a newly-active chart's canvas stayed frozen at its original (often 0×0) size for as long as updates kept flowing. Confirmed directly by watching `canvas.width` stay 0 through repeated `chart.resize()` calls while Test Mode's updates kept streaming, until `chart.stop()` (cancels the in-flight animation) was called first.

The real, correct fix is architectural: `BASE_OPTS.scales.x` is `type:'linear'` (real epoch-ms values, not category/string labels), and every chart point is a genuine `{x: epoch-ms, y: value}` pair (`safeUpdateChart(chart, times, values)` zips `historyTimes`/`history[k]` into these; the multi-chart's datasets in `applyHistory()` do the same). A point's (x,y) never changes after it's first recorded — confirmed by watching one sample's exact `{x,y}` stay bit-for-bit identical across ticks while `scales.x.min`/`max` advanced. Because of that, every still-visible point simply lands at a slightly different pixel position each redraw (its fixed timestamp falling in a different spot within the advancing `[min,max]` window) — which alone reads as continuous smooth scrolling at 5 redraws/second, the same way a heart-rate monitor trace looks fluid from frequent redraws with no animation system involved. `animation:false` again (no `LIVE_ANIMATION`), `chart.update('none')` always — there's nothing left for Chart.js's animator to usefully tween, and the whole resize-deferral trap is moot as a result. `attachTimeAxis(opts)` (assigns the x-tick formatter and tooltip title formatter — both functions, so like `attachHaptics()` this has to run *after* `JSON.parse(JSON.stringify(BASE_OPTS))`, not live on `BASE_OPTS` itself) needs to be called for any future chart built off `BASE_OPTS`, same as `attachHaptics()`. `forceChartResize()` (`stop()` then `resize()`) is kept as a defensive no-cost guard against this trap ever recurring, not because it's load-bearing today.

### Live chart history is a single GROWING buffer with a global time-RANGE toggle — not a fixed-size ring anymore
`history[k]`/`historyTimes` used to be a fixed-size ring (`MAX_POINTS`, shift-then-push, capped at ~30s/12s desktop/mobile). Replaced with a growing buffer per metric, retained until `HISTORY_HARD_CAP_MS` (4h) regardless of what's currently selected for display, plus a separate global `currentRangeMs`/`currentRangeKey` (`RANGE_OPTIONS`: 1/5/15/30 min or `null`/`'all'` for "All") that's just a VIEW into a slice of that buffer — switching ranges never re-fetches or discards data, it only changes which slice `applyHistory()` hands to Chart.js.
**UI is a row of buttons per page, not one dropdown** — `renderRangeToggles()` renders identical `.range-toggle-btn` markup into every `[data-range-slot]` container (one above the charts on each of the 8 dedicated pages, one inside Overview's Customize panel — Overview's own mini-charts don't get a visible row of their own, folded into Customize instead since that's already where Overview's other chart-display settings live), all reflecting/controlling the SAME shared state via one delegated `document` click listener. An earlier version used a single `<select>` in the header — replaced because the user wanted the control visible above the graphs on each page instead. If a page renders charts and doesn't have a `[data-range-slot]` in its markup, its charts still obey the global range correctly, they just have no on-page way to change it from that page.
**"All" means "the current continuous run", not the full DB-backed session.** This is a deliberate scope line matching this file's existing documented split between the client-side-only live charts and the separate, durable, server-side Sessions/CSV-export feature (see the Sessions rules elsewhere in this file) — a session's full pre-page-load history is what the Sessions tab already exists for; merging that fetch into the live charts here was a deliberately avoided scope expansion, not an oversight. "All" is still bounded by `HISTORY_HARD_CAP_MS`, same as every other range, and further scoped by the stale-gap-cutting rule below.
`findTimeIndex()` (binary search on the always-ascending `historyTimes`) finds the window's start index in O(log n) rather than a linear scan — matters because the buffer can hold tens of thousands of entries at the long-range end. `chartIsVisible()` (checks `canvas.offsetParent !== null`) gates which charts `applyHistory()` actually rebuilds each tick — rebuilding a data array that can now be 1,500-9,000+ points for every one of ~25 charts every 200ms, whether visible or not, was the exact kind of cost already fixed once this session (see the Test Mode paint-starvation rule elsewhere in this file) and would reintroduce it at this new, larger scale. A chart naturally catches up within one poll tick of becoming visible (`applyHistory()` re-runs on every new live packet regardless of the active tab) — EXCEPT when nothing is live (offline, or Test Mode off), which is why the tab-click handler explicitly calls `applyHistory()` itself right after the existing `forceChartResize()` calls, not just relying on the next packet that might never come.
`safeUpdateChart(chart, times, values, xMin, xMax)` takes explicit x-axis bounds now (used to derive them from `times[0]`/`times[last]`) — the selected window can be much wider than however much real data has actually arrived, and the axis needs to show the FULL currently-effective window immediately (see the grow/gap-cutting rule below for how that window is computed), not shrink-wrap to whatever data exists so far.
Decimation (Chart.js's built-in plugin for exactly this "many points, narrow chart" scenario) was deliberately NOT added — it looked like the right tool for the 15/30-min-range point-density concern, but requires `parsing:false` and specific data-shape assumptions this environment couldn't visually verify render correctly, so it was left out rather than risk an unverifiable rendering bug. Worth reconsidering if long-range charts turn out to look/perform poorly on a real device.

### A live chart's window GROWS from a 1-minute floor up to the selected range, and RESETS on a stale gap — `activeRunStart`/`CHART_GAP_STALE_MS`
Two asks that turned out to be the same underlying mechanism: (1) a chart shouldn't jump straight to a mostly-empty full-range window the instant a run starts — it should start small and grow into the selected range as real time actually elapses; (2) a >5s gap in live data (LoRa dropout, agent restart, car parked) shouldn't have Chart.js draw a straight line bridging the dead time as if it were a continuous reading. Both are handled by one pair of variables tracked in `pushHistory()`: `lastPacketTime` (the previous real packet's timestamp) and `activeRunStart` (when the CURRENT uninterrupted run began). If a new packet arrives more than `CHART_GAP_STALE_MS` (5000ms) after `lastPacketTime`, the entire retained buffer is wiped and `activeRunStart` resets to that new packet — no attempt to render a visual "gap" mid-chart, the chart just re-anchors cleanly to the new run, discarding the disconnected old one (this applies even in "All" mode — see its own rule above).
`applyHistory()` computes the actual displayed window from this: `effectiveSpan = max(RANGE_FLOOR_MS, min(now - activeRunStart, currentRangeMs))` (or, for "All", `max(RANGE_FLOOR_MS, now - activeRunStart)` with no upper term). `RANGE_FLOOR_MS` (60000, 1 minute) is the floor mentioned above — even the instant the very first packet of a fresh run arrives, the chart shows a 1-minute-wide axis, not a razor-thin one that stretches wider with every single point. As real time elapses past that floor, the window grows 1:1 with elapsed time until it reaches `currentRangeMs`, then holds/slides at that fixed width like before. Verified directly: faking `activeRunStart` to different ages produces exactly 60000ms (floor, <1min elapsed), 120000ms (mid-growth, 2min elapsed), and 300000ms (capped at a 5min selection, 20min elapsed) window spans; and a manually-pushed packet timestamped >5s after the last one drops the buffer from 104 points to 1 while a <5s gap leaves it untouched.

### Session charts (`viewSession()`) intentionally were NOT converted to the {x,y}/linear-axis pattern
They're one-shot static renders built once from a session's full history, not incrementally updated — the "index reassignment" problem above only exists for a *shifting* window, which a static array never has. They still use label-array/category-axis Chart.js config; no need to touch them if the live-chart x-axis approach changes again.

### ⚠️ (Historical — see RESOLVED note above) The Inno Setup `.exe` was UNSIGNED and got blocked on Intune-managed/WDAC-enforced devices — reproduced firsthand, not theoretical
The user tried the real download on their own machine and hit `"Windows cannot access the specified device, path, or file. You may not have the appropriate permissions to access the item."` when running it. Diagnosed directly (`dsregcmd /status`, `Get-AuthenticodeSignature`, `citool.exe --list-policies`, `icacls`): the machine is Azure-AD/Intune-enrolled, and `Get-AuthenticodeSignature` itself got `UnauthorizedAccessException` on the file despite normal-looking ACLs (Full Control listed for the owning account) — the signature of Windows Defender Application Control (WDAC) blocking an unrecognized/unsigned binary at the OS level, not an actual filesystem permission problem. Smart App Control was confirmed OFF (`VerifiedAndReputablePolicyState:0`) at the time, so it's specifically WDAC/org policy via Intune, not SAC.
**This isn't one machine's quirk — it's structural.** Any similarly-managed device (very plausibly most/all of this team's org-issued laptops, if they're on the same tenant policy) will hit the same block. The user was told this explicitly and chose to **leave the installer live anyway** rather than revert to the old `greenpower-agent.zip` fallback — a deliberate, informed call, not an oversight. Don't "fix" this by silently reverting to the zip; that decision was already made.
**Self-signing was tried and empirically ruled out TWICE, not just assumed unhelpful.** Generated a self-signed code-signing cert (`New-SelfSignedCertificate`) and attempted to sign the installer with `signtool.exe` (obtained standalone via the `Microsoft.Windows.SDK.BuildTools` NuGet package — much lighter than installing the full Windows SDK, no admin needed) — **`signtool` itself got blocked before it could touch the file**, with the exact same "Access is denied" symptom, in a scripted/headless attempt. The Windows event log (`Microsoft-Windows-Windows Defender/Operational`, event ID 1121) named the precise cause: **ASR rule `01443614-cd74-433a-b99e-2ecdc07bfc25`**, *"Block executable files from running unless they meet a prevalence, age, or trusted list criteria."* That rule name is the important part — it's reputation-based (built up over time/download volume in Microsoft's cloud intelligence), not simply "is this file signed." A self-signed cert has zero reputation, identical to an unsigned file, so it would not have helped even if signing itself hadn't also been blocked.
The user then independently ran the exact same `New-SelfSignedCertificate`/`signtool sign` commands themselves, interactively, in their own visible PowerShell window — **identical "Access is denied" failure.** This rules out the one remaining theory (that a scripted/headless attempt might simply be missing an interactive override prompt a human would see and could click through) — there is no such prompt for this rule in this configuration; it's a hard block with zero user-facing override, enforced the same way regardless of who or how it's invoked. Don't re-attempt self-signing as a workaround without new information (e.g., the org's ASR policy actually changing) — this has been conclusively tested twice, not just reasoned about.
This also means **a freshly-issued real Azure Artifact Signing certificate might not immediately clear this specific rule either** — signing helps most against SmartScreen and general trust, but this particular ASR rule is stricter than that; a brand-new signed file may still need to build up download reputation before this rule stops flagging it. All private key/cert material generated for these tests was deleted after each finding — nothing was left lying around unused.
**The real fix is code-signing** (researched, not yet started, and per the above, not guaranteed to fully resolve this specific ASR rule on its own): Microsoft's **Azure Artifact Signing** (rebranded from "Trusted Signing" in 2026, ~$9.99/mo Basic tier) is the realistic path given this org is already on Azure AD — but it requires a live, webcam-based government-photo-ID identity verification (via AU10TIX) tied to one specific real person (not the team/org — a passport/driver's license/state ID, explicitly not a student ID), 1-20 business days of Microsoft processing after that, and an Azure subscription with an Individual-type billing account (or a full Organization identity validation instead, if there's a registered legal business entity — more paperwork, not obviously easier). None of this can be completed by an AI assistant — it needs a specific human's real ID and live phone. If this gets set up later, wiring the resulting cert into the build is the easy part: Inno Setup's `[Setup]` section supports `SignTool=` directly.
**The likely faster real fix: ask the org's IT to add an ASR exclusion** for this specific file/app — sidesteps identity verification, cost, and reputation-building entirely, since it's a policy exception rather than a trust mechanism. This needs the org's actual IT/Intune administrator, not something achievable from a single machine.

### Chart tooltips disappear immediately when a touch is released — `attachTouchTooltipAutoHide()`
Chart.js's default `events` list includes `touchstart`/`touchmove` (so scrubbing a finger across a chart shows/updates the tooltip) but **not** `touchend` — there's no touch equivalent of a desktop `mouseout` to clear it, so on a touch device the tooltip used to just stay pinned at wherever the finger last was, indefinitely, until the next tap started a new one. `attachTouchTooltipAutoHide(chart)` adds real `touchend`/`touchcancel` listeners on `chart.canvas` that clear it instantly (`chart.setActiveElements([])` + `chart.tooltip.setActiveElements([], {x:0,y:0})` + `chart.update('none')` — the standard documented Chart.js pattern for programmatically hiding a tooltip, `'none'` mode for no fade). **An earlier version faded it out after a 1s delay instead** — the user tried that behavior and asked for an immediate disappearance in its place, so if a delay/fade ever seems worth reintroducing, confirm that's actually wanted first, it was a deliberate choice already made once here.
Unlike `attachHaptics()`/`attachTimeAxis()` (which patch an **options object** before `new Chart(...)` is called, since those get `JSON.parse(JSON.stringify(BASE_OPTS))`-cloned per chart), this one takes the **chart instance itself** and must run *after* construction (`attachTouchTooltipAutoHide(new Chart(...))`) — it needs `chart.canvas`/`chart.update()`, which don't exist until the chart is actually built. Wired into all three chart-construction sites: `safeChart()` (ov/big charts), the multi-chart, and each `viewSession()` session chart. `TOOLTIP_OPTS.animation` (`{duration:250}`) still governs the tooltip's own show/appear transition (unaffected by this — only the hide path uses `'none'`), separate from the chart-level `animation:false` used everywhere else in this file.

### Mobile nav sheet's CLOSE animation was silently skipped — `display:none` doesn't wait for a transition
Real bug, not a duration/easing issue: `.mobile-navsheet`/`.mobile-navsheet-backdrop` used to be in the same "hidden by default" `display:none` selector as the rest of the mobile-only UI, with `.show` explicitly setting `display:block`. Opening worked fine (transitioning from a `display:none` starting point into visible is a normal, supported browser pattern) — but *closing* did not: removing `.show` reverted to the base rule's unconditional `display:none`, which isn't a transitionable property and takes effect the instant the class changes, yanking the sheet out of rendering before its opacity/transform transition got even one frame to play. It just vanished instead of animating out. Fixed by pulling both elements out of that shared `display:none` selector entirely and relying purely on `opacity:0`/`pointer-events:none` for the closed state (verified structurally both directions using this project's documented transition-disable trick — see the tooltip rule near the bottom of this file). Costs nothing extra on desktop: both are `position:fixed`, already out of normal layout flow, so being "always rendered but invisible" has no layout effect there. If a similar show/hide-via-`.show`-plus-`display:none`-base-rule pattern is used for a future element that needs a close animation, this is the same trap — don't reach for `display:none` as the closed state if a close transition matters.

### `.chart-hide-btn`'s icon is centered with flex, not text-align/line-height
`text-align:center` + `line-height:<button-height>px` only centers on a text baseline — it doesn't reliably vertically-center a differently-sized inline-flex child (the `.icon` span, 10×10 inside an 18×18 circle), and visibly lands off-center depending on the icon's own metrics. `display:flex; align-items:center; justify-content:center` on the button centers by actual box geometry instead, regardless of icon size — the fix, if a similar tiny-icon-in-a-circle-button pattern is added elsewhere.

### `color-scheme: dark` (meta tag + CSS) — separate from `theme-color`, needed for OS-drawn chrome (status/nav bar)
`theme-color` only tints the in-browser tab/address-bar strip. The OS-level chrome around an *installed* PWA (Android's status bar AND bottom gesture/nav bar) follows the page's declared `color-scheme` in current Chrome, not `theme-color` — without it, that chrome can default to the system light/dark setting regardless of how dark the page itself is. Declared both as `<meta name="color-scheme" content="dark">` and `:root{color-scheme:dark}` (belt-and-suspenders — different engines/contexts read one or the other). Still won't retroactively fix an *already-installed* copy of the app without an uninstall+reinstall (manifest/meta values are cached at install time) — see SESSION_NOTES.md.

### Mobile edges are tinted to match Android's *actual* system-bar colors — the opposite approach from `theme-color`/`color-scheme`
After confirming (via the Chromium issue tracker, a matching bug report against another unrelated PWA, and MDN's own docs never actually claiming navigation-bar control in the first place) that `theme-color`/`color-scheme` genuinely can't reliably make Android's system bars match the page — this flips the direction: match the page's edges to what Android is *actually* painting instead. Two DIFFERENT measured values, not one — the status bar (top) and gesture/nav bar (bottom) are not the same color on this device: **`#0b0c11`** (status bar — nearly identical to `--bg0` already, a 1-unit difference) and **`#171719`** (nav bar — a real, visible difference from `--bg0`). An earlier pass used a single `#5f5f5f` for both; that measurement was wrong/stale and has been fully replaced — if you see `#5f5f5f` referenced anywhere, that's stale. Both are user-measured constants sampled directly off the real installed app, not derived from anything else — if Android's actual bar colors ever shift (device/OS update), these need resampling, not a formula fix.

Scoped to mobile only, in four places:
1. `body { background:#0b0c11; }` inside `@media(max-width:860px)` — the status-bar value. `#app` carries its own explicit `background:var(--bg0)` on desktop (added specifically for this; it had none before, relying on `body` showing through), so `body`'s mobile color is only ever visible in the genuine top edge gap (`safe-area-inset-top` strip above `#header`) — **never** the bottom, since `#app`'s box already extends the full `100dvh` down to the physical bottom edge, leaving no gap there for `body` to show through at all.
2. `#app { background:linear-gradient(to bottom, #0b0c11, #171719 80%); }` (mobile-only override, replacing the flat `var(--bg0)`) — this is what actually carries the bottom-edge (nav-bar) fix, since `body` structurally can't reach there (see above). A full-height gradient, not a separate bottom-only strip: both endpoints are close near-black tones, so it reads as "a background" across the whole scrollable dashboard, not a visible seam partway down the page — and `--panel` (the card overlay, a barely-there 3.5% white tint tuned for a near-black base) still reads fine against either end, unlike the earlier flat-`#5f5f5f`-everywhere attempt would have.
   The second stop is pinned at **80%, not 100%**. A plain 2-stop gradient (`A, B`) only reaches the *exact* second color at the very last pixel row — measured directly: the nav bar pill sits at roughly 92-99% down a typical phone viewport, where a 100%-terminated gradient was still interpolating to something like `#161619` instead of the true `#171719` — a real, if small, off-by-one-unit mismatch, not the exact measured color. Per the CSS gradient spec, once a gradient passes its *last* explicit color stop, the color holds exactly constant for the rest of the box — no further interpolation — so pinning the stop at 80% guarantees the entire nav bar/sheet zone (with comfortable margin for a shorter device or more safe-area inset pushing the pill up further) sits on the *exact* measured `#171719`, not an approximation of it.
3. `#header { background:#0b0c11; }` (mobile-only override, flat and opaque — NOT the desktop `rgba(13,16,23,.85)`). Two real problems with reusing the desktop translucent tint here: it has a visible blue cast (blue channel 23 is the highest of the three; `#0b0c11`'s channels are much closer to neutral), and being translucent it blends with whatever's scrolling behind it rather than staying one fixed color — both read as a mismatch against the real, neutral, opaque status bar directly above it. Flat+opaque fixes both.
4. A second, `media="(max-width: 860px)"`-gated `<meta name="theme-color">` tag (`#0b0c11`) alongside the existing unconditional one (`#0a0c11`) — same mechanism browsers already use for `prefers-color-scheme` light/dark variants, so desktop's tab/toolbar tint is completely untouched. A single flat meta value can't represent the top/bottom split the way `#app`'s gradient does — this only ever represents the top.

`manifest.json`'s `background_color`/`theme_color` are `#0b0c11` (top/status-bar value — these only ever apply to the mobile PWA install/splash-screen context, so no mobile-only gating needed, and a splash screen is a single flat color with no gradient concept anyway).

### Scrollable+rounded elements use `overflow: hidden auto` (or `auto hidden`), never a bare `overflow-y:auto`/`overflow-x:auto`
`#raw-log`, `#sessions-table-wrap`, `.mobile-navsheet` all combine `border-radius` with scrolling. A bare `overflow-y:auto` leaves `overflow-x` at its default `visible` — but per the CSS Overflow spec, a box can't have one axis `visible` and the other not, so the un-set axis gets silently computed to `auto` too. That implicit second scrollbar axis was what let the (custom-styled, `::-webkit-scrollbar-*`) scrollbar draw outside the element's own border-radius curve on some browsers/devices — the user's literal report was seeing it "go past rounded edges." Explicitly setting the axis that's genuinely never wanted to `hidden` (not just leaving it unset) avoids the dual-auto computation instead of fighting it after the fact. `#sessions-table-wrap` scrolls horizontally (`overflow:auto hidden`) while the other two scroll vertically (`overflow:hidden auto`) — match the direction to whichever axis that specific element actually uses.

### `.mobile-navbar`'s drop shadow is symmetric (zero offset), not upward-biased and not a plain downward one
Went through four states this session: a plain downward shadow (`0 10px 30px -10px rgba(0,0,0,.6)` — cast a dark halo/gradient into the ~10px+ gap toward the real Android nav bar below it, reading as a color mismatch even once the actual background colors, see `#app`'s gradient rule above, were correct) → removed entirely (the safe fallback while nothing else was resolved) → upward-biased (`0 -2px 8px rgba(0,0,0,.3)`, negative y-offset, once the user asked for the pill to have real depth back) → **`0 0 6px rgba(0,0,0,.3)`, equal on every side**, per an explicit follow-up request for symmetric depth rather than a lopsided lift. With zero offset, the shadow's downward reach past the element's own bottom edge is the FULL blur radius (6px here, not `blur − |offset|` the way the upward-biased version's was) — kept deliberately small so that full reach still stays inside the ~10px+ measured gap; a bigger blur here would need an offset again to stay clear, they trade off against each other. Since `.mobile-navbar` only ever renders on mobile (base rule is `display:none`, only turned on inside `@media(max-width:860px)`), this lives on its unconditional base rule rather than needing a mobile-only override. If this pill's height/position or the gap to the real nav bar ever changes meaningfully, re-verify that 6px reach still clears it (see the `.mobile-navsheet` shadow rule below for how to actually measure that gap, not just assume it from the raw CSS `bottom:` values).

### `.mobile-navsheet-backdrop`'s dimming fades out before it reaches the nav bar — the real source of the "big black shadow", not the sheet's own box-shadow
After tightening the sheet's own `box-shadow` (below), the user reported the shadow reaching the nav bar was still there — the real culprit was different: `.mobile-navsheet-backdrop` (the full-screen `rgba(0,0,0,.45)` dimming overlay behind an open sheet, `position:fixed; inset:0`) covers the *entire* viewport, and while the nav bar pill itself sits above it in z-index (`.mobile-navbar` is z-index 15, backdrop is 14 — the pill's own opaque pixels are genuinely untouched), the small gaps/margins/rounded corners *around* the pill are still part of "the page behind the sheet" and were getting darkened by that same flat 45% black — reading as a big shadow reaching the nav bar, distinct from (and much larger than) the sheet's own small box-shadow. Fixed by making the backdrop's `background` a gradient instead of a flat color: full 45% dimming holds through 70% down the viewport (still dims the actual page content behind the sheet, the whole point of a backdrop), then fades smoothly to `rgba(0,0,0,0)` by 84% — the nav bar pill's own top edge measures ~91.6% down a typical phone (same measurement used for the `#app` gradient fix above), leaving a real ~7-8% margin, not just enough to technically clear it. If the nav bar's position or height ever changes, re-check that 84% still lands comfortably before its new top edge.

### `.mobile-navsheet`'s drop shadow was removed entirely (not just tightened)
Same root problem as `.mobile-navbar` above, one step removed: the sheet floats *above* the nav bar pill, and its original shadow (`0 18px 44px -14px rgba(0,0,0,.65)`) reached far enough down to still visibly darken the gap toward the pill below, perturbing the same precisely-tuned background. A first attempt tightened it to `0 8px 20px -6px rgba(0,0,0,.5)` (~28px reach) reasoning the sheet-to-pill gap was ~78px — but the ACTUAL measured gap (sheet's real bottom edge to the pill's real top edge) is only **~4-10px**, since `bottom:calc(78px+safe-area-inset-bottom)` on the sheet and `bottom:10px+safe-area-inset-bottom` + 58px height on the pill nearly cancel out. No shadow size can both read as a real depth cue and clear a gap that small, so this went to `box-shadow:none` entirely — same call already made for `.mobile-navbar`, same reasoning, just a step later. If the sheet's `bottom` offset or the pill's height/position ever change enough to meaningfully widen this gap, a real shadow could be reconsidered — but always measure the ACTUAL rendered gap first (`getBoundingClientRect()` on both, not the CSS `bottom:` values alone), not just assumed from the raw CSS numbers.

### `display: "standalone"` (not `"fullscreen"`) — tried and deliberately reverted
Even with `theme_color`/`background_color`/`color-scheme` all correctly matching `--bg0`, the installed-PWA (WebAPK) navigation bar still didn't reliably pick up that color — a real, documented Chromium/Android platform limitation: full, reliable system-bar-color control only exists for a proper Trusted Web Activity (a native Android wrapper app, not a plain "Add to Home Screen" WebAPK). `display_override:["fullscreen","standalone"]` was tried as a workaround (hides the OS status/nav bar entirely instead of trying to color-match it) but the user found fullscreen mode itself buggy on their device and asked to revert — so the color mismatch stands as a known, currently-unresolved limitation of the plain-WebAPK install path, not something to re-attempt via `display_override` without the user explicitly asking again. If this needs revisiting, the only remaining real lever is a proper Trusted Web Activity wrapper (Bubblewrap or similar) with its own `navigationColor` field — a materially bigger undertaking (native build/signing, likely Play Store or sideload distribution) than anything achievable purely from `manifest.json`/CSS.

### The mobile nav sheet only lists tabs NOT already in the fixed bottom bar
`.mobile-navsheet` used to duplicate all 12 tabs, including the 5 marked `.mobile-navbar-tab-primary` that are already one tap away in the bar itself. It now lists only the other 7 (`temperature`/`imu`/`raceline`/`link`/`multi`/`sessions`/`raw`) plus `settings` (which has no primary-bar slot). The bar's own hidden `.mobile-navbar-tab` entries (non-primary, `display:none`, kept in the DOM purely for the shared `.tab` active-class-sync loop) still list all pages including `settings` — don't confuse "not shown in the bar" with "not present in the bar's markup", those are two different things for two different reasons (visibility vs. click-handler/active-sync wiring).

### Tapping anywhere on the mobile toolbar closes an open nav sheet, and doubles as the toolbar's haptic tap
