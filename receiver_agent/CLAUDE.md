# CLAUDE.md — Receiver Agent

**This file is a briefing for an AI assistant.** Read it before touching any code in this folder.

---

## What This Project Is

A local background script (Node.js) that runs on whatever computer the [`greenpower_receiver`](../greenpower_receiver/CLAUDE.md) ESP32 gets plugged into over USB. It watches for new serial ports, positively identifies whether a newly connected device is actually the Greenpower receiver (not some other USB device), and — critically — **asks the user before forwarding anything**, via an OS notification. Only on acceptance does it start relaying parsed telemetry to [`telemetry_web`](../telemetry_web/CLAUDE.md)'s `/api/telemetry` endpoint.

As of V1.4 it also: **auto-updates itself** (checks a small manifest on the same dashboard host, silently downloads+installs a newer `.msi` if one's published), and has a **local GUI** — a loopback-only status/log page opened from a new "Show GUI" tray item, with a real **Uninstall** button that does a genuine, complete removal. See the dedicated rules below for all three.

The three-part system: `greenpower_receiver` (ESP32, LoRa → USB serial) → **this folder** (watches USB, prompts, forwards) → `telemetry_web` (always-on public site).

This is meant to run continuously in the background (e.g. started at login), not launched manually each time — see `README.md` for the Windows auto-start setup.

## Rules and Constraints

### Never forward without asking — this is the whole point of this agent existing
`promptToForward()` is not optional and not a "nice to have" — the user explicitly asked for consent-based forwarding rather than silent auto-start, specifically because a website that's always live but only shows real data when a human opted in on that specific machine was the desired behavior. Don't add a "remember my choice, don't ask again" auto-accept mode without the user asking for it — that would defeat the reason this agent exists rather than the website talking to the ESP32 directly.

### Device identification is handshake-based, not just "any serial port"
`identifyPort()` doesn't assume a new serial port is the receiver just because it appeared — it opens the port, sends `ID?\n`, and waits for the `DEVICE_ID` string (`GREENPOWER_RX_V1`) to show up, either from the firmware's boot beacon (if the agent was already watching when the device powered up) or the on-demand reply. Ports that don't answer within `IDENTIFY_TIMEOUT_MS` are marked `'not-ours'` and left alone. This must match `DEVICE_ID` in `../greenpower_receiver/greenpower_receiver.ino` exactly — if that firmware constant changes, update it here too.
**`ID?\n` is now retried every 500ms for the whole identify window, not sent once — a real, confirmed bug, found via a user report of "no forward notification" that turned out to have nothing to do with the port itself.** Root cause: opening a Node `serialport` connection to an Arduino-style board commonly toggles DTR, which triggers a genuine hardware RESET on boards using an auto-reset circuit (this receiver included) — the ORIGINAL single `ID?\n` write, sent the instant the port opened, could race that reset and land while the board was still rebooting, well before its own `while(!Serial) ... < 3000` boot wait finished and `loop()`/`pollIdentityRequest()` was even running to see it. Confirmed via `agent.log`: the port opened successfully (no "Access denied"), Device Manager showed it as a genuinely working COM port, and yet the identify attempt still produced zero output before an eventual disconnect — exactly the signature of a lost one-shot write, not a broken port. Fixed by retrying the write every 500ms until either `DEVICE_ID` is seen or the identify window expires — a write lost to an in-progress reset costs nothing, and whichever retry lands after the board's actually finished booting gets answered.
**`IDENTIFY_TIMEOUT_MS` bumped from 4000ms to 6000ms in the same pass** — with the board's worst-case ~3s boot wait, the original 4s window left almost no margin for a retry to land, get answered, and for that answer's data event to actually fire before timing out.
**The timeout branch now logs when it gives up, which it never did before — a real diagnostic gap, not just a missing nicety.** A port that opens fine but never answers `ID?` used to produce NO line in `agent.log` at all — indistinguishable from "nothing was ever tried" and the actual thing that made this bug hard to see in the first place (the log showed the port later "disconnected" with no attempt ever visible in between). It now logs `"<port> didn't answer the identify handshake within <N>ms — assuming it's not the Greenpower receiver."` — if this line starts showing up for the real receiver's port, that's a sign something is STILL wrong with the handshake (wrong firmware flashed, wrong baud rate, a different bug) even after the retry fix, not something to ignore. **This line is exactly what surfaced the SF10 receiver-firmware hang** (see `greenpower_receiver/CLAUDE.md`'s matching ⚠️ rule) — the port opened fine, but the board never answered because it had hung in `radio.begin()` before ever reaching `loop()`/`pollIdentityRequest()`. Nothing wrong with the agent in that case; the timeout log doing its job is what made the real (firmware-side) problem visible.
**A second, near-identical silent gap found and fixed in the same live-debugging pass**: `identifyPort()`'s synchronous `try { new SerialPort(...) } catch (e) { ... }` branch — distinct from the async open-error callback right next to it, which already logged — set `knownPorts` to `'not-ours'` with **zero log output**, ever. A port hitting this path was indistinguishable from one that was never even attempted. Fixed the same way as the timeout branch: log the caught error's message before marking it `'not-ours'`.

### `knownPorts` forgets a port when it disappears, on purpose
So unplugging and replugging the same physical receiver re-triggers the full identify → prompt flow rather than silently doing nothing (or silently resuming forwarding without asking again). Don't "fix" this into a persistent allow-list unless the user specifically asks for that — it would also mean silent forwarding after the first plug-in, which contradicts the consent requirement above.

### `node-notifier`'s response casing is not reliable — always compare case-insensitively
The prompt uses `actions: ['Yes', 'No']`, which on Windows (SnoreToast backend) renders as real toast buttons. This caused a real, confirmed bug: SnoreToast returned the response as lowercase `'yes'` even though the button was defined as `'Yes'` — a strict `response === 'Yes'` check silently treated every acceptance as a decline, so clicking "Yes" never started forwarding and looked from the user's side like the whole system was broken. The fix is `response.toLowerCase() === 'yes'`; don't go back to an exact-case string match. A `[DEBUG]` log line prints the raw `response` value on every prompt — leave that in, it's what caught this bug and will catch the next backend-specific surprise.

### Success/failure confirmation notifications fire once per connection, not per packet
`startForwarding()` tracks `confirmed`/`failureNotified` in closure state scoped to that one port connection. The first successful forward triggers a one-time "Forwarding live telemetry..." toast; if the *first* attempt fails and nothing has succeeded yet, a one-time failure toast fires instead. Don't move this logic into `forwardLine()` itself or make it fire on every call — at the sender's ~500ms packet rate, a real outage would otherwise spam a failure toast twice a second.

### Fetch requires Node 18+
`forwardLine()` uses the global `fetch` built into Node 18+, no `node-fetch` dependency. If this ever needs to run on an older Node version, that's a real added dependency, not just a version bump.

### `agent.pid` is what makes `setup.bat` idempotent — don't remove it
The agent writes its own PID to `agent.pid` on startup. `setup.bat` reads that file and `taskkill /F`s the old process before launching a new one, every time it's re-run. Without this, re-running `setup.bat` (e.g. to pick up a code change) piles up multiple hidden `node.exe` instances — this actually happened once: an old instance held a serial port open, and the new instance's `SerialPort.list()`/open attempt failed with "Access denied" on that port, which looked like a hardware/driver problem but was really just a stale process fighting the new one for the same port. If you change how the agent is launched (e.g. a different auto-start mechanism), keep an equivalent single-instance guard.

### ⚠️ `agent.js` itself also enforces single-instance now — via an atomic lock DIRECTORY, not a PID file (a real race was found and fixed in the PID-file version)
The check above (`setup.bat`'s own `taskkill`) only covers "someone re-runs `setup.bat`" — it does nothing for every OTHER way a second instance could start (the Startup-folder auto-launch firing on login while a previous instance is somehow still alive, someone double-clicking the launcher shortcut a second time, running `node agent.js` manually while the hidden auto-started one is already up, an auto-update's freshly-launched instance briefly overlapping the one it's replacing). `acquireSingleInstanceLock()` runs before anything else in `agent.js` and closes this for every one of those cases.

**First version of this used a plain `agent.pid` file (read, decide, then write)** — genuinely broken under a real race, confirmed via a direct two-instance launch test (not a hypothetical): two processes started within milliseconds of each other could both read the file before either had written its own PID, both concluded "I'm first," and **both ended up running** — exactly the "fighting over one serial port" failure this guard exists to prevent.

**Fixed with an atomic lock DIRECTORY** (`.agent.lock`, inside the install folder) — `fs.mkdirSync()` either creates it or throws `EEXIST`, atomically, with no window where two processes can both "succeed" at that specific call. On `EEXIST`, the losing process reads the PID recorded inside the lock dir (`'.agent.lock/pid'`) and either `SIGTERM`s the owner if it's still alive, or — if the owner's PID file can't be read yet — **waits and retries rather than deleting the lock**.

**⚠️ That last part was itself a second real race, found the same way (a live test, not reasoning about it)**: `mkdirSync()` and the *separate* `writeFileSync()` that records the owner's PID inside it are two distinct synchronous calls, not one atomic operation. A losing process can see `EEXIST` from the directory existing, but read the pid file a few microseconds *before* the owner has actually written its PID into it — getting an empty file / `NaN`. The original fix treated any unreadable pid as "stale, delete it" — which deleted a lock the other process had *just* created, and let both processes create fresh locks and both survive, confirmed via debug logging (`dbg()`, temporarily added and since removed — see git history/this rule if it needs to come back) showing the exact sequence. The actual fix: `couldReadPid` distinguishes "genuinely stale" (a parseable PID that isn't alive — safe to clean up) from "owner is still mid-write" (an unparseable PID — wait and retry without touching the lock; the owner is nanoseconds from finishing). **Verified with a real two-instance race test, run 10+ times in a row with zero failures after the fix** — one prior version of this passed a single test run and still failed intermittently (~1-in-5) on repeated runs, which is why this was tested repeatedly, not just once, before being called fixed.

`agent.pid` (plain file, root of the install folder) still exists alongside `.agent.lock` — kept for `setup.bat`'s own external `taskkill`-based check and as a human/tool-readable "what PID is this" record, but it is **not** the actual mutual-exclusion mechanism anymore; `.agent.lock` is. Don't revert to reading `agent.pid` for any new single-instance logic — reproduce the exact race above.

### `log()` timestamps every line, not just the session start
Needed for real diagnosis — a burst of identical errors within milliseconds (e.g. duplicate processes fighting over one port) looks identical to the same errors spread across a 20-second window in an unstamped log, and those two situations point at completely different root causes. Keep per-line timestamps if `log()` is ever refactored.

### The `log()` helper exists because the agent runs invisibly — don't call `console.*` directly
`setup.bat` registers the agent to run via a hidden `wscript`-launched process with no visible window (`WshShell.Run "node agent.js", 0, False`), so `console.log`/`console.error` output goes nowhere anyone can see. Every message in this file goes through `log()`, which writes to both stdout (useful for the manual `npm start` path) and `agent.log`. If you add new log output, use `log()`, not `console.*` directly, or it'll be invisible in the normal (hidden, auto-started) way this actually runs.

### `agent.log` is truncated fresh on every start, not appended forever
By design — this agent deliberately doesn't log per-packet forwarding activity (only state changes: found/prompted/forwarding/errors), so log volume per run stays small and a fresh-per-run log is simpler than rotation. Don't add per-packet logging to `forwardLine()`'s success path — that would both spam `agent.log` and make the file grow unbounded on an agent left running for weeks.

### The tray icon is a genuine npm package named `systray`, not `node-systray` or `node-systray-v2`
Confirmed by actually installing it — `node-systray`/`node-systray-v2` are the GitHub repo/fork names (and what a lot of copy-pasted READMEs/tutorials show as the import), but the package actually published to npm is called `systray` (`npm i systray`). It's a CommonJS default export, so `require('systray').default`, not `require('systray')` directly (verified empirically — `require('systray')` returns `{ default: SysTrayClass }`). Menu items need all four fields (`title`/`tooltip`/`checked`/`enabled`) — they're non-optional in the type. `action.seq_id` in `onClick()` is the item's index in the `items` array (index 0 = the disabled "Running" status line, index 1 = "Stop Agent" here). `kill(false)` stops the tray helper process without also calling `process.exit()` itself — this agent already has its own `process.on('exit', ...)` cleanup (PID file + tray) shared by every exit path, so the click handler just calls `process.exit(0)` and lets that shared cleanup run once, rather than duplicating it inline.

### Tray icon failures are non-fatal — losing the tray icon must never take down forwarding
`new SysTray(...)` and its `onError` handler are wrapped so a tray-init failure (e.g. running on a Windows build/permission setup where the tray helper binary can't launch) only logs a `[WARN]` and continues — actual telemetry forwarding is this agent's real job and shouldn't depend on a status icon succeeding. If the tray ever needs to become load-bearing for something, that's a deliberate design change, not a refactor.

### Restarting the agent is required to pick up agent.js changes — it doesn't hot-reload
Obvious in hindsight but worth stating: a code change here (like the tray icon addition) only affects the *next* time the agent starts (re-run `setup.bat`, or `taskkill` the old `node.exe` per `agent.pid` and start it again) — an already-running instance keeps running the code it loaded at its own startup.

### Why `.msi` (WiX), not `.exe` (Inno Setup) — a real, confirmed platform constraint, not a preference
The Inno Setup `.exe` was built first, worked, and was live on the dashboard — then the user tried the real download on their own (Intune-managed) machine and hit a hard OS-level block: `Get-AuthenticodeSignature` on the file itself threw `UnauthorizedAccessException`, traced to Microsoft Defender ASR rule `01443614-cd74-433a-b99e-2ecdc07bfc25` ("block executable files unless they meet a prevalence, age, or trusted list criterion"). Self-signing was tried and empirically ruled out TWICE (once scripted, once by the user themselves interactively) — it's a hard block with no override, and its documented scope is specifically `.exe`/`.dll`/`.scr`. An `.msi` isn't a raw PE executable — `msiexec.exe` (already trusted) does the actual installing — so it was tried next and **confirmed empirically exempt**: `Get-AuthenticodeSignature`/file-read on a freshly-built, zero-reputation `.msi` completed cleanly, and the user confirmed the real install completes successfully on the same machine the `.exe` was blocked on. Full investigation, exact commands, and exact event-log evidence: `telemetry_web/CLAUDE.md`. **Don't revert to the `.exe` as the distributed installer without new information** (e.g., the org's ASR policy changing) — this was conclusively tested, not just reasoned about. `GreenpowerAgent.iss` (Inno Setup) is kept in the repo as historical/dormant, not deleted, in case `.msi` distribution itself ever becomes a problem for some other reason — but it's not what `telemetry_web` currently links to or what `README.md` currently documents.

### The installer (`installer/GreenpowerAgent.wxs`) duplicates `setup.bat`'s logic in WiX custom actions — keep them in sync
`GreenpowerAgentSetup.msi` is the primary distribution now (linked from both the dashboard's Download Installer button and the repo root README), but `setup.bat` still exists and still works standalone — they're independent implementations of the same steps (`npm install`, register a hidden Startup-folder launcher, launch now), not one calling the other. If the setup FLOW itself changes (a new step, a different auto-start mechanism, a new prerequisite check), update both — the `.wxs` file's `CustomAction`/`InstallExecuteSequence` entries and `setup.bat` will silently drift apart otherwise. (The dormant `GreenpowerAgent.iss`/Inno Setup `[Code]` section is a THIRD independent implementation of the same logic, from when the `.exe` was the live distribution — not actively kept in sync, don't assume it still matches either of the other two without checking.)
**No admin rights, deliberately**: `Package InstallScope="perUser"` (a WiX v3 attribute that handles the underlying ALLUSERS/MSIINSTALLPERUSER MSI properties automatically) + installing under `LocalAppDataFolder\Programs\GreenpowerAgent` means the installer never triggers a UAC prompt and never needs Program Files — matters because whoever's running this on a laptop at the track may not have admin on that machine. Don't change the install directory to a Program Files path or otherwise make this require elevation without a real reason. This is the same underlying goal `PrivilegesRequired=lowest` served in the dormant Inno Setup version.
**Per-user MSI components trip several WiX ICE validation rules a per-machine install wouldn't** — real, documented WiX/MSI requirements, not workarounds: ICE38 requires a per-user-profile component's KeyPath to be an HKCU registry value, not a file (every `<File>` in `AgentFiles`/`AgentConfig` dropped `KeyPath="yes"` in favor of a dedicated `<RegistryValue>`); ICE64 requires an explicit `<RemoveFolder On="uninstall">` for every per-user-profile directory in the tree, including the shared parent `Programs` folder (safe — `RemoveFolder` only deletes it if it ends up actually empty, never force-removes another app's stuff sitting in a sibling subfolder). If a future edit adds a new per-user Component, it needs the same registry-KeyPath + RemoveFolder treatment or the build will fail the same way.
**`npm install` runs via `WixQuietExec` (from `-ext WixUtilExtension`), not a plain `ExeCommand="cmd.exe /c npm install"`** — a real bug, not a style choice: the plain form popped a visible console window during install (the user's own report). `WixQuietExec`'s contract is specific and easy to get subtly wrong: for a *deferred* action, the command line must come from a `<Property>` with the exact same `Id` as the `<CustomAction>` — but that `<Property>` itself must be set via an *immediate* `<CustomAction Property="..." Value="...">` (which formats/resolves `[INSTALLFOLDER]`-style references when it runs), never a bare static `<Property Id="..." Value="...">` (which does NOT get formatted — `candle`'s own `CNDL1077` warning catches this specific mistake; don't ignore that warning here even though its own wording says it might be a false positive for a "string literal" — in this exact pattern it wasn't). `RunNpmInstall_SetProperty` (immediate, sets+formats the property) must be scheduled `Before="RunNpmInstall"` (the deferred exec) in `InstallExecuteSequence`.
**Only one Start Menu shortcut (the app launcher), a plain non-advertised one — no separate explicit "Uninstall" shortcut, and a genuine advertised shortcut was tried and confirmed NOT to work here.** History, in order: an explicit second "Uninstall" shortcut (`Target="[SystemFolder]msiexec.exe" Arguments="/x [ProductCode] /qb"`) was added after an initial report that right-click-to-uninstall wasn't appearing → removed at the user's request once a screen recording showed Windows' right-click → Uninstall DOES appear (routing to Settings → Apps) → the user clarified that specific working right-click was on the *explicit uninstall shortcut itself*, confirmed by a follow-up recording that the plain launcher's right-click only offers "Open file location", no uninstall entry → the user asked for a real "normal Windows" uninstall (i.e. the actual native mechanism, not a second shortcut standing in for it) → **tried, and hits a genuine, confirmed WiX/MSI validation conflict, not a guess**: an advertised shortcut (`Advertise="yes"`, nested inside the `<File>` it launches — this IS what makes Windows recognize a Start Menu entry as "belonging" to an installed product and offer native Uninstall) requires its component's KeyPath to be a FILE (ICE19/ICE50), but every per-user-profile component here is required to use an HKCU REGISTRY KeyPath instead (ICE38, see the rule above) — directly contradictory requirements for the same component, reproduced via an actual failed build (`LGHT0204` ICE19/ICE50), not reasoned about abstractly. Splitting the shortcut's file into its own separate component doesn't help — that component is still per-user-profile and hits ICE38 the same way. The only real ways around it are going per-machine (needs admin/UAC — defeats the entire reason this installer is `InstallScope="perUser"`) or suppressing ICE validation (the shortcut would then not actually resolve correctly at runtime — worse than the current state). Bottom line, independent of any shortcut behavior: this is a real registered MSI product, so **Settings → Apps → Installed apps** (or Control Panel → Programs and Features) will always list it for uninstall — that's the guaranteed path for this per-user install type, and there is currently no way to also get a native Start-Menu-right-click uninstall without giving up the no-admin install. Don't re-attempt the advertised-shortcut route without new information (e.g. deciding a per-machine/admin install is acceptable after all).

### ⚠️ REAL, CONFIRMED bug: removing that second "Uninstall" shortcut without bumping `Version` broke install/uninstall/shortcuts entirely
The removal above (the "mobile settings page" commit, deleting the `StartMenuUninstall` `<Shortcut>` from `Component Id="StartMenuShortcut"`) changed that Component's set of resources — but left BOTH the Component's GUID (`3e2a2f9d-...`, unchanged) AND the `<Product>` `Version` (`1.2.0.0`, unchanged since the very first commit that added this file) exactly as they were. **This is a genuine, well-documented Windows Installer rule violation, not a style nit**: once a component's GUID is published, its resource list is meant to be immutable — Windows Installer tracks "what a component owns" by GUID, not by re-diffing the current source on every install. Changing a component's contents while its identity (GUID) AND the product's overall version both stay the same leaves the installed system's bookkeeping out of sync with what the package actually contains, and this is genuinely undefined/unreliable by MSI's own design, not something `candle`/`light` can catch at compile time (no ICE rule flags it). **Confirmed on real hardware**: a user report of install "not working correctly," files left behind after uninstall, and the Start Menu shortcut not working — all three symptoms, exactly what this class of bug produces, traced directly to this one commit via `git log`/`git show` (the diff itself, not speculation).
**Fixed by bumping `Version`** — a proper `MajorUpgrade` version bump forces Windows Installer to cleanly uninstall the entire old product first (by `ProductCode` swap, not a component-by-component diff) before installing the new one, sidestepping the whole class of component-identity confusion rather than trying to reconcile it. **The rule going forward, now spelled out in a comment right above `<Product>` in the `.wxs` itself**: any time a Component's set of File/Shortcut/RegistryValue children changes at all — even with the Component's own GUID left alone — `Version` must be bumped in the same change. This wasn't caught before shipping because a version bump has no compile-time enforcement and the broken install/uninstall behavior only shows up on a REAL machine that already had the previous version installed, not on a first-ever install (which is why this went unnoticed through a normal edit-rebuild-eyeball-the-file review cycle).
**This fix WAS rebuilt and republished, in a later pass in the same session** — a portable WiX v3.14.1 toolchain (`candle.exe`/`light.exe`) was obtained specifically to do this (not available in the environment that made the initial source fix), and `telemetry_web/public/GreenpowerAgentSetup.msi` now reflects it — verified directly against the built `.msi`'s own `Property`/`Shortcut` tables, not just assumed from the source. Current version is `1.3.1.0` (bumped once more in the same session for an unrelated `agent.js` content fix — see the identify-handshake rule elsewhere in this file — each real change gets its own bump, per the rule above). Anyone who already installed the originally-broken version should still manually clean up first (Settings → Apps → uninstall, then check `%LOCALAPPDATA%\Programs\GreenpowerAgent` for leftover files and delete by hand if the uninstall didn't clear it) before installing the fixed one, since the broken version's own uninstall can't be trusted to have cleaned up correctly.
**Node.js is still a required prerequisite, not bundled.** Packaging the agent into a single, fully standalone executable (via `pkg` or Node's built-in Single Executable Applications feature) was considered and deliberately not attempted — `serialport` is a native addon and `systray` spawns its own helper binary, and bundling native addons into a SEA/pkg single-file executable is a known-fragile combination with edge cases this environment couldn't verify actually work on a real target machine. If that's ever attempted, treat it as a real project with real device testing, not a quick swap.

### `setup.bat`'s config-write block avoids delayed-expansion pitfalls on purpose
The `set /p` + config.json write logic uses `goto`/labels instead of nesting inside an `if (...)` parenthesized block — batch expands `%VAR%` at parse time for a whole parenthesized block, so a variable set with `set /p` earlier in the *same* block reads back empty. If you touch `setup.bat`, keep variable-set-then-use sequences as separate top-level lines (or add `setlocal enabledelayedexpansion` + `!VAR!` if you reintroduce a block) rather than reintroducing this bug.

### Auto-update — a static manifest, not a server endpoint
`checkForUpdate()` fetches `<dashboard-origin>/agent-version.json` (`AGENT_VERSION`'s comparison target) — a **plain static file** in `telemetry_web/public/`, not a server route. `telemetry_web` already serves that folder as-is (`express.static`), so this needed zero server code — same "rebuild by hand, it's a snapshot" pattern the `.msi` itself and the old `greenpower-agent.zip` before it both already use (see `telemetry_web/CLAUDE.md`).
**This file MUST be updated (bump `version`, keep `msiUrl` pointing at the same published `.msi` path) every single time a new `.msi` is built and published** — it's a separate file from the `.msi` itself, nothing enforces they move together automatically. Forgetting this means already-installed agents simply never see the update; they'd keep polling and finding "nothing newer" even though a new `.msi` is sitting right next to the manifest.
`AGENT_VERSION` (top of `agent.js`) must exactly match both `GreenpowerAgent.wxs`'s `<Product Version="...">` AND the manifest's `"version"` field for that build — three places, same number, none of them auto-derived from the others. `isNewerVersion()` does a plain dotted-quad numeric compare (not semver) since MSI `Version` fields are always exactly that 4-part numeric shape.
On finding a newer version: downloads the `.msi` to `%TEMP%`, writes a disposable VBS helper (`writeUpdateHelperVbs()`) that waits for THIS process's PID to fully exit before running `msiexec /i ... /qn`, then this process exits. Waiting for the PID first is deliberate — Windows Installer replacing `agent.js` (and other installed files) while this same process still has them loaded is exactly the kind of race an unattended background updater must not risk. `GreenpowerAgent.wxs`'s existing `<MajorUpgrade>` element handles cleanly replacing the old version; its existing `LaunchAgentNow` CustomAction (unchanged) starts the new version immediately after install — nothing extra needed on the agent side for either of those.
Checked once ~15s after startup (let the agent settle first) and then every `UPDATE_CHECK_MS` (6h) — see `guiState.update` for what the GUI's status page reads to show checking/installing/available state.

### The GUI is a genuine native WinForms window, not a browser tab — the HTTP server underneath is just its data layer
Direct ask, not a style choice: "Show GUI" opens a real Win32 window (`openNativeGuiWindow()`/`guiWindowPs1()`), not `http://127.0.0.1:.../` in the default browser. **No GUI-toolkit dependency added for this** — no Electron, no nw.js, both real, heavy additions this project's existing "keep dependencies minimal" pattern (and the installer's whole no-admin/small-footprint design) argue against. Instead: `.NET`'s WinForms is already on every Windows machine this targets, reached by shelling out to `powershell.exe` (`Add-Type -AssemblyName System.Windows.Forms`) — the exact same "shell out to PowerShell for something Node can't do natively" pattern this file already uses for the ProductCode COM lookup. `guiWindowPs1()` generates the form's full source fresh into `%TEMP%` on every click (small, disposable, not worth caching).
**The window is a pure client of this agent's own existing loopback HTTP API** — `Invoke-RestMethod` against `$apiBase/api/status` and `$apiBase/api/log` on a 3s `System.Windows.Forms.Timer`, POSTing to `/api/check-update`/`/api/uninstall` from the two buttons. The API itself didn't need to change at all for this — only how it's *presented* to the user did. `guiPageHtml()`'s browser-page route (`GET /`) is kept as a working fallback reachable by navigating there directly (e.g. if PowerShell/WinForms were ever unavailable) — nothing currently links to it, "Show GUI" no longer opens a browser.

### ⚠️ REAL, CONFIRMED bug: `{ detached: true }` silently breaks `powershell.exe`'s own argument handling on Windows — took a controlled A/B test to actually find
A real user report ("Show GUI doesn't work") led to this. `powershell.exe` visibly ran (present in Task Manager, `Responding: True`) but no window ever appeared — no crash, no error, nothing. Two earlier, plausible-sounding theories were tested and DISPROVEN before the real cause was found, worth recording so they aren't re-tried:
1. *"`-WindowStyle Hidden` on `powershell.exe` suppresses the WinForms window itself, not just the console — switch to a `wscript.exe` VBS wrapper instead."* Disproven — the VBS-wrapped launch failed identically.
2. *"`powershell.exe` defaults to MTA; WinForms needs STA."* True and `-STA` is correct/necessary (kept in the final fix) — but adding it alone did NOT reliably fix the failure across repeated tests, so it wasn't the (whole) story either.

**The actual root cause**, found via a controlled test that spawned `powershell.exe -Command "exit 42"` four ways and compared the resulting exit codes:
```
{ detached: true, stdio: 'ignore' } → exit code 0   (WRONG — command never ran)
{ detached: true }                  → exit code 0   (WRONG — command never ran)
{}                                  → exit code 42  (correct)
{ stdio: 'ignore' }                 → exit code 42  (correct)
```
**`{ detached: true }` on Windows silently breaks `powershell.exe`'s own `-Command`/`-File` argument handling** — the process starts, does nothing at all (not even an error), and exits 0, as if no command had been given. This has nothing to do with `-WindowStyle`, STA/MTA, WinForms, or anything on the launched-script side — it reproduced with a trivial `exit 42`, no GUI involved at all. `detached` was never actually needed for `openNativeGuiWindow()` in the first place — `child.unref()` alone already accomplishes "don't let this hold the agent's event loop open," which was the entire reason `detached` got added originally. **Fix: `openNativeGuiWindow()`'s spawn call has no `detached` option at all now** — just `{ stdio: 'ignore' }` + `child.unref()`.
Note this is specific to `powershell.exe`, confirmed by contrast: the update/uninstall helpers' `spawn('wscript.exe', [...], { detached: true, stdio: 'ignore' })` calls elsewhere in this file DO work correctly with `detached: true` (verified via real install→update/uninstall cycles) — don't assume this bug applies to every `spawn()` call in this file, only to `powershell.exe` specifically.
**Verified fixed via a controlled test through the EXACT real production launch chain** (`msiexec`'s `LaunchAgentNow` → `agent-launcher.vbs` → `node.exe` → the GUI spawn), not just an ad-hoc script — 3 consecutive clean successes (real `MainWindowTitle`/`Responding` checks) after the fix, versus consistent failure before it, both reproduced through that identical chain.
Still loopback-only underneath (`startGuiServer()` binds `http.createServer(...).listen(GUI_PORT, '127.0.0.1', ...)` — the explicit `'127.0.0.1'` bind address is load-bearing, not incidental; omitting it defaults to all interfaces) — this must never be reachable from anything but processes on the same machine. No auth beyond that (loopback-only IS the security boundary here) — don't add a route that trusts a request just because it arrived, without first checking whether that assumption still holds if this ever changes to bind more broadly.
No framework for the server side either — routes (`/`, `/api/status`, `/api/log`, `/api/check-update`, `/api/uninstall`) hand-rolled on Node's built-in `http` module, deliberately not Express, matching this project's existing "keep dependencies minimal" pattern (see `package.json`'s own short dependency list — unchanged by any of this).

### ⚠️ The Uninstall button — real, hard-won lessons on what "zero trace" actually requires
This took three real, empirically-found bugs to get right — not reasoned about in the abstract, each confirmed via an actual install→uninstall cycle on a real machine before being called done:
1. **`msiexec /x` needs a ProductCode, and there's no fixed one to hardcode.** `GreenpowerAgent.wxs` uses `Id="*"` (a fresh ProductCode every build) — only `UpgradeCode` is fixed. A first attempt scanned `HKCU\...\Uninstall` via `reg query /s` for a matching `DisplayName` — **confirmed wrong**: a per-user (`InstallScope="perUser"`) install doesn't register there at all; its real registration lives under `HKLM\...\Installer\UserData\<user-SID>\Products\<COMPRESSED GUID>\InstallProperties`, keyed by a byte-swapped "packed" GUID encoding, not the standard dashed form `msiexec /x` needs. The actual fix: `findInstalledProductCodes()` asks the Windows Installer COM API directly — `Installer.RelatedProducts(upgradeCode)` — the same mechanism Windows itself uses, returning real, standard-format ProductCode(s) for a given UpgradeCode. Shelled out via `powershell.exe` (Node has no native COM support; not worth a new dependency for one lookup) — the same `New-Object -ComObject WindowsInstaller.Installer` pattern this project's own build-verification steps already use elsewhere.
2. **There can genuinely be more than one ProductCode under the same UpgradeCode at once.** Confirmed by accident during testing: installing two builds sharing the same `Version` (not bumped between them) left both registered side-by-side, and `MajorUpgrade` didn't collapse them since neither was strictly newer than the other. `findInstalledProductCodes()` (plural) returns every match, and the uninstall helper `msiexec /x`s all of them — uninstalling only the first found would leave a real, confirmed orphan (still in Settings > Apps, still holding `HKLM` `UserData` registration) — the opposite of "zero trace". In normal usage (auto-update always bumps `Version`) this shouldn't come up, but the fix costs nothing to keep as a defensive measure.
3. **The hardest one: the install folder itself resisted deletion with `Err.Number 70` ("Permission denied") — a TOKEN problem, not a file lock, and not fixable from `agent.js`'s side at all.** The agent process an uninstall gets triggered from can be one `msiexec`'s own deferred, **impersonated** `LaunchAgentNow` CustomAction started (`Impersonate="yes"` in the `.wxs`) — this fires on every fresh install AND every auto-update (see the auto-update rule above), not just a one-off first-install edge case. That impersonated token lineage is nominally "the same user" but doesn't reliably carry the same delete rights on its own just-installed files as an ordinary interactive logon session does. Three things that did NOT fix it, each confirmed by testing and re-checking, not assumed: retrying the delete repeatedly with pauses (ruled out a timing/lock race — a manual delete from an interactive session always succeeded *instantly*, every time, no matter how long the automated attempts had already been failing); explicitly resetting ownership/ACLs (`takeown` + `icacls`) immediately beforehand (ruled out because those ran as a *child* of the same restricted token, which inherits it and gains nothing); and escaping via a one-time Scheduled Task (`schtasks /create ... /sc once`, a standard technique for exactly this class of problem in general) — created successfully, but never actually fired in testing (`Last Result: 267011`/never-run, well past its scheduled trigger time), most likely due to Task Scheduler's default "only run when this user is logged on" condition not recognizing whatever session type this testing environment presented, an uncertainty this project can't fully resolve or trust for a real end user's machine either.
   **The actual fix lives in `GreenpowerAgent.wxs`, not `agent.js`** — a dedicated `RemoveAgentRuntimeFiles` CustomAction (immediate `_SetProperty` + deferred `WixQuietExec` pair, same structural pattern as `RunNpmInstall` above) that removes `node_modules`/`agent.log`/`agent.pid`, scheduled `Before="RemoveFiles"` with condition `REMOVE="ALL"` (fires on real uninstall and on the old-product-removal half of a MajorUpgrade, not on repair) — **and, critically, `Impersonate="no"`**, deliberately unlike every other CustomAction in this file. That runs it as the Windows Installer service's own account rather than impersonating whatever token invoked `msiexec /x` — sidestepping the token problem entirely, and as part of the SAME transaction rather than a separate, less certain mechanism after the fact. This has the added benefit of also cleaning up correctly for anyone who uninstalls via Settings > Apps directly, bypassing the GUI's Uninstall button entirely — the earlier `agent.js`-only approaches never would have covered that path. `agent.js`'s own `writeUninstallHelperVbs()` now only does a small best-effort `fso.DeleteFolder` retry loop (up to 90 attempts, ~90s) as insurance for a separate, smaller, genuinely benign timing quirk: an already-EMPTY folder (confirmed via direct inspection — all real content is gone within seconds via the CustomAction above) can still report as existing for well over a minute after `msiexec /x` returns, observed up to ~80s+ in testing, before clearing on its own — a manual delete of that same empty folder always succeeded instantly whenever actually tried, confirming this is NOT the permission problem recurring, just an OS/NTFS-level settling delay this project can't fully explain or control.
4. **⚠️ A real, confirmed bug the retry loop above ITSELF caused: reinstalling within that ~90s retry window could get the fresh install's own files deleted out from under it.** User-reported and reproduced: uninstall via the GUI, reinstall soon after (a completely reasonable thing to do — nothing suggests waiting), and the reinstall would fail/be corrupted. Root cause: the retry loop's `fso.DeleteFolder(installFolder, True)` was RECURSIVE and unconditional on every one of its 90 attempts, with no check for what might legitimately be at that path by the time a later retry fired — a reinstall starting during that window populates the exact same `INSTALLFOLDER` path with real, brand-new files, and the leftover script from the PREVIOUS uninstall would delete them, having no way to tell "my own old empty leftover" apart from "someone's live reinstall." **Fixed by checking the folder is genuinely empty (`folder.Files.Count = 0 And folder.SubFolders.Count = 0`) immediately before every single delete attempt, and stopping the retry loop entirely (not deleting, not looping again) the moment it isn't** — a leftover from the triggering uninstall is always empty by this point (real content already removed via the CustomAction above), so anything with actual files in it by the time a retry runs is, by construction, never this uninstall's own leftover. **Verified by reproducing the exact failure scenario**: uninstall → reinstall 5 seconds later (well inside the old 90s danger window) → confirmed the new install's files survived the FULL remaining ~90s of the old leftover script's retry window untouched.

The full flow (`triggerUninstall()` → `writeUninstallHelperVbs()`): find every related ProductCode → write a disposable VBS to `%TEMP%` that waits for this agent's PID to exit → `msiexec /x` each ProductCode found (the real, registered uninstall — removes every MSI-tracked File/Shortcut/RegistryValue, delists from Settings > Apps, and via the un-impersonated `RemoveAgentRuntimeFiles` CustomAction, also the untracked `node_modules`/`agent.log`/`agent.pid`) → a best-effort, empty-check-gated retry loop for the top-level folder entry itself (see bug 3 and bug 4 above) → explicit Startup-shortcut + registry cleanup as belt-and-suspenders → self-delete. **Verified end-to-end on real installs repeatedly** (not just read through) — installed fresh, confirmed running via the GUI, clicked-equivalent (`POST /api/uninstall`), and confirmed ALL of: process gone, install folder gone, Startup shortcut gone, `HKCU\Software\Greenpower\ReceiverAgent` gone, zero `RelatedProducts` remaining for the UpgradeCode — AND (bug 4's own test) a reinstall started moments after uninstall survives the old leftover script's full retry window.
If this is ever touched again: re-verify with a real install→uninstall→reinstall cycle, the same way — the whole reason this took four passes to get right is that each of these problems produces no compile-time warning and looks fine on a first read of the code.

## Current State (V1.11/V2.3 — real "reinstall right after uninstall" bug found and fixed: leftover cleanup was deleting the new install)
