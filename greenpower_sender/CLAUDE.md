# CLAUDE.md — Greenpower Sender

**This file is a briefing for an AI assistant.** Read it before touching any code in this folder.

## What This Project Is

The **real** telemetry sender for the Greenpower vehicle, currently built on a **breadboard** around a Heltec ESP32-S3 LoRa WiFi V4. It reads live sensors, prints the results to USB serial, and transmits on two radio links at once: **LoRa** (on-board SX1262, binary `telemetry_packet_t`) for a future long-range base-station receiver, and **ESP-NOW** to the steering wheel [`display_receiver`](../steering_wheel_display/CLAUDE.md) (same CSV format as [`mock_sender`](../mock_sender/CLAUDE.md), so the receiver doesn't care which sender is live).

The ESC/UART link (dropped in the V2 rework, since the breadboard build didn't have the ESC controller connected at the time) is **back as of V3.1** — see [`esc controller`](../esc%20controller/CLAUDE.md), now running on an ESP32 WROOM-32. Both LoRa and ESP-NOW carry real ESC data; the ESP-NOW placeholder fallback (`"---"`, `0.0`) only kicks in if no ESC UART line has ever been parsed.

## Hardware (breadboard, all point-to-point wiring)

| Signal | ESP32-S3 pin | Component |
|---|---|---|
| GPS RX (from GPS TX) | GPIO34 | Adafruit Ultimate GPS Breakout V3, Serial1 |
| GPS TX (to GPS RX) | GPIO33 | " |
| I2C SDA | GPIO17 | shared bus: IMU + ADS1115 |
| I2C SCL | GPIO18 | " |
| Temp probe (1-Wire digital) | GPIO6 (needs 4.7kΩ pull-up to VCC) | DS18B20 |
| Motor RPM | GPIO4 | laser-interrupt disc sensor, unbranded |

| ESC TX (to ESC RX) | GPIO43, Serial2 | wired for symmetry — the ESC's firmware doesn't currently read anything back |
| SD card CS | GPIO47 | own SPI bus, see the dedicated rule below |
| SD card SCK | GPIO48 | " |

| SD card MISO | GPIO5 | " |
| RTC SDA | GPIO1 | second/independent I2C bus (`Wire1`), see the dedicated rule below |
| RTC SCL | GPIO2 | " |

**LoRa (on-board SX1262):** NSS=8 RST=12 DIO1=14 BUSY=13, SPI SCK=9 MISO=11 MOSI=10. 915 MHz, **SF7, BW500** (latency now explicitly prioritized over range — SF7 is the lowest value already proven safe on this hardware; BW raised from 125→500 for the actual range-for-latency trade, ~36ms time-on-air per packet — see the dedicated rule below), sync word 0xF3, 22 dBm — see `config.h`.

**ADS1115 (Lonely Binary board, I2C addr 0x48)** — shared bus with the IMU:
| Channel | Signal |
|---|---|
| A0 | motorVolt, via 5:1 voltage divider (VCC < 25 V) |
| A1 | battVolt, via 5:1 voltage divider (VCC < 25 V) |
| A2 | Vout — YHDC HSTS016L 100A current sensor output |
| A3 | Vref — YHDC HSTS016L reference, read directly (no assumed zero) |

**IMU** is an HW-123 breakout (MPU6050-compatible), read with `Adafruit_MPU6050` at the default address `0x68`.

### Critical: ADS1115 must be powered from 5V, not 3.3V
The voltage-divider channels (A0/A1) can swing up to ~5V (25V max input ÷ 5:1 divider). If the ADS1115's VDD is 3.3V, those channels will clip regardless of gain setting. Wire ADS1115 VDD to a 5V rail.

## Rules and Constraints

### `config.h` is shared — coordinate before changing it
`telemetry_packet_t` (73 bytes, packed), the LoRa RF settings, and `ESPNOW_PEER_MAC` are meant to be identical on both ends of each link. There **is** a LoRa receiver in this repo now ([`greenpower_receiver`](../greenpower_receiver/CLAUDE.md)) and its `config.h` must be updated in the same commit as this one — they're two independently-maintained copies, not a shared include, so nothing enforces this automatically. Update the size comment whenever a packet field is added, removed, or reordered.

### ESC UART link — real data as of V3.1, not placeholders
`pollEsc()` runs every `loop()` iteration (same pattern as `pollGps()`) reading CSV lines off Serial2 from [`esc controller`](../esc%20controller/CLAUDE.md)'s `throttle_controller.ino`: `mode,state,setpointPct,livePct,rampPct`. Parsed values land in the module-level `esc` struct; `updateSensors()` copies them into `pkt.esc_*` and sets `PKT_FLAG_ESC_VALID` only once a line has actually been parsed (`esc.valid`) — don't assume the ESC fields are populated from boot, a disconnected/not-yet-booted ESC controller means the flag stays clear and `pkt.esc_*` stays zeroed.
- `esc.mode`/`esc.state` are 8-byte buffers (`char[8]`), matching `telemetry_packet_t.esc_mode`/`esc_state` exactly — this isn't arbitrary, the ESC's own `snprintf` truncates those fields to 7 chars (`%.7s`) before sending, so 8 bytes (7 + null) is exactly enough and intentionally not more.
- `parseEscLine()` bails out early (via early `return`) on any missing comma-separated field, leaving whatever was already in `esc.*` from the previous good line untouched — a single malformed/truncated UART line doesn't corrupt or blank out the last known good ESC state.

### ESP-NOW packet format — must match `mock_sender` and `display_receiver`
```
speed_mph,batV,rpm,amps,mode,state,setpoint%,live%,ramp%
```
Produced by `espNowSend()`, must stay field-for-field identical to what `mock_sender.ino` sends (see [`mock_sender/CLAUDE.md`](../mock_sender/CLAUDE.md)) and what `display_receiver`'s `parsePacket()` expects. `mode`/`state`/the three percent fields now come from the real ESC link (`pkt.esc_*`, gated on `PKT_FLAG_ESC_VALID`) — the `"---"`/`0.0` placeholders only fire if no ESC UART line has ever been successfully parsed since boot, not as a permanent stand-in.

### ESP-NOW peer MAC — critical
`ESPNOW_PEER_MAC` in `config.h` must match the MAC address `display_receiver` prints on boot. Currently `{0x44, 0x1B, 0xF6, 0xCA, 0x38, 0xE4}` — same value used by `mock_sender`, so the two senders are interchangeable from the receiver's point of view.

### ✅ CORRECTION — the SF10/SF12 "hangs" documented below were a flashing mistake, NOT a real radio.begin()/spreading-factor incompatibility
**Per direct user confirmation**: the boards failing to boot/respond at SF10 and SF12 (both documented in detail below, and mirrored in `greenpower_receiver/CLAUDE.md`) were caused by an incorrect flashing procedure on the user's end at the time, not a genuine hardware or RadioLib limitation with this board at higher spreading factors. **The caution elsewhere in this file (and in `greenpower_receiver/CLAUDE.md`) against trying SF8-SF12 no longer applies** — there is no known reason this board can't run any valid spreading factor; the whole "untested/hung territory" framing used to justify staying at SF7 through several later passes (the latency work, the BW125 range pass) was based on this since-corrected assumption. The narrative below is kept intact as real history (the async-TX rework it produced, the SPI-sharing bug it led to finding, are all still genuinely useful) — just don't treat "SF10/SF12 hangs this board" as a still-true fact when reasoning about future range/SF changes.

### ⚠️ (HISTORICAL — see ✅ CORRECTION above) SF12 was tried for range, confirmed to HANG the board on real hardware, and has been fully reverted to SF7 — don't re-attempt without solving the hang first
Full story, since the reasoning below (async TX, separate intervals) is real and still worth understanding even though the SF change itself didn't ship: after a real-world report of the sender/receiver disconnecting at ordinary walking distance, LoRa was moved from SF7 to SF12 (max spreading factor = max range) on both sender and receiver, along with two changes SF12's ~3.8s time-on-air made necessary — an async TX rework (`startTransmit()`/`setPacketSentAction()`/`finishTransmit()`, mirroring the receiver's existing interrupt-driven RX pattern, since a blocking `radio.transmit()` at that airtime would freeze the whole `loop()`, ESP-NOW included) and a separate, much slower `LORA_TX_INTERVAL_MS` decoupled from ESP-NOW's own interval.
**This shipped, was flashed to real receiver boards, and the boards stopped responding over USB serial entirely** — no boot beacon, no reply to the `ID?` identify handshake `receiver_agent` depends on, confirmed via Arduino IDE's own Serial Monitor showing NOTHING printed at all, on more than one board. Since `Serial.println(DEVICE_ID)` executes before `radio.begin()` in `setup()`, and `pollIdentityRequest()` runs unconditionally on every `loop()` iteration regardless of radio state, a total absence of ANY serial output — not even the boot line — means `setup()` itself never returned, which points squarely at `radio.begin()` with the SF12 parameter actually HANGING (not cleanly erroring, which the code was defensively written to handle) inside RadioLib's SX126x configuration sequence. This was reasoned as a real risk before shipping (see the removed comments' own discussion of low-data-rate-optimization, required automatically by RadioLib for SF11/SF12 at BW125) but not something testable without real hardware — and once tested, it failed.
**Reverted in full at the time** — both `.ino` files went back to byte-identical (content-wise) with the pre-SF12 commit: spreading factor back to 7, intervals back to one shared 200ms/5Hz constant, `loRaTx()` back to a plain blocking `radio.transmit()` call, no async-TX plumbing. This was a deliberate choice to fully back out rather than guess at a smaller step while ALSO trying to fix a live, multi-board, real-world-blocking failure — isolating variables mattered more than preserving partial progress at the time.

### (HISTORICAL — see ✅ CORRECTION above) SF10 — the second attempt, ALSO confirmed to hang on real hardware, reverted
Per explicit follow-up request to re-attempt max range "but don't break anything this time": **SF12's root cause was never actually confirmed**, only reverted, so going straight back to it would have been re-betting on the same unverified assumption that just cost multiple bricked boards. SF10 was chosen instead as a smaller, better-reasoned step: its time-on-air (~944ms for the pre-shrink packet) keeps its symbol duration under the 16ms threshold that requires RadioLib to enable low-data-rate-optimization for SX126x — the leading (at the time, unconfirmed) suspect for what hung at SF11/SF12.
**What shipped at the time**: spreading factor 10 on both sender and receiver, `LORA_TX_INTERVAL_MS` ~2s (real headroom above the ~944ms airtime), and the SAME async-TX rework from the SF12 attempt reintroduced (`startTransmit()`/`setPacketSentAction()`/`finishTransmit()`, `loraTxInFlight`/`loraTxDoneFlag`/`checkLoraTxComplete()`).
**⚠️ CONFIRMED to also hang on real hardware, in a later pass**: after the receiver was reflashed with SF10 (plus the `epoch_time`/`hdop_x10`/`esc_mode_code` packet changes), it produced zero serial output at all — not even the boot beacon that prints before `radio.begin()` — confirmed via a raw serial sniff independent of `receiver_agent` that received exactly 0 bytes over 5 seconds. See `greenpower_receiver/CLAUDE.md`'s matching ⚠️ rule for the full diagnosis (this was found while debugging an unrelated "no forward popup" report from `receiver_agent` — see that project's own CLAUDE.md too). **The LDRO-threshold theory that justified trying SF10 is now a disproven predictor** — SF10 sits below that threshold and hung anyway, so whatever actually hangs this board's `radio.begin()` at higher spreading factors isn't (purely) an LDRO effect.
**Reverted back to SF7 on both sender and receiver.** Kept from the SF10 attempt: the async-TX machinery (still strictly safer than a blocking `transmit()` regardless of spreading factor, and costs nothing at SF7's much shorter ~144ms airtime) and the separate `LORA_TX_INTERVAL_MS`/`ESPNOW_TX_INTERVAL_MS` constants (shrunk `LORA_TX_INTERVAL_MS` back down to 200ms to match SF7's actual airtime, rather than leaving it at the SF10-sized 2s unnecessarily). **The underlying range problem (sender/receiver disconnecting at ordinary walking distance) is unsolved again** — two independent spreading-factor increases (SF12, SF10) have now both hung this exact board's `radio.begin()`. Don't try SF8/SF9 (or SF10/SF12 again) without new information about *why* `radio.begin()` hangs at some spreading factors and not others on this specific board — this may not be a LoRa-parameter-tuning problem at all. If range is revisited, test one spreading factor at a time on ONE board with a Serial Monitor attached, and consider it might need a different approach entirely (e.g. investigating RadioLib GitHub issues for this exact chip/board combo) rather than just picking a different SF value.

### ⚠️ Real, unrelated bug found in this same window: the SD card's SPI bus was silently sharing hardware with the LoRa radio's own SPI
Fully explains a live user report ("hit yes on the agent, it doesn't forward") that initially looked like it might be yet another receiver hang, but wasn't. `sdSPI` was `SPIClass(FSPI)` — on the ESP32-S3, arduino-esp32's own default `SPI` object (what the LoRa radio's `SPI.begin(LORA_SCK, ...)` call uses) is ITSELF internally `FSPI`, so `sdSPI` was never a genuinely separate peripheral, just a second C++ object pointing at the same one. Since ESP32 SPI peripherals route pins through an internal GPIO matrix, `initSdCard()`'s `sdSPI.begin(SD_SCK_PIN, ...)` — called after LoRa's own init — silently reprogrammed the SHARED peripheral's pin routing to the SD card's pins, out from under the radio. `radio.begin()` (runs first) kept succeeding; every subsequent `radio.startTransmit()` (runs later, in `loop()`, after the hijack) failed — confirmed via a live serial sniff of the sender showing `[LoRa] startTransmit() ERR -1` on every single attempt, **at SF7**, the original known-good setting, which is what proved this was never actually a spreading-factor problem.
**Fixed by moving `sdSPI` to `HSPI` (SPI3_HOST)** — genuinely independent hardware from `FSPI`, not just different pins on the same peripheral. **This bug had been latent since the SD card feature was first added** — it needed SD logging AND a receiver actually listening for real packets exercised together to surface, which apparently hadn't happened until this pass. **This does NOT explain or fix the SF10/SF12 receiver hangs above** — those are a separate, still-unresolved problem on the RECEIVER (which has no SD card, no FSPI conflict); don't conflate the two if either resurfaces.
**The general lesson for this board, beyond just this one bug**: "give a peripheral its own `SPIClass` instance on different pins" does NOT guarantee independent hardware on the ESP32-S3 — check which peripheral host (`FSPI`/SPI2 vs `HSPI`/SPI3) is actually requested and confirm nothing else (including the default `SPI` object) already uses that same host, regardless of pin numbers.

### ⚠️ THIRD range attempt: SF12 + BW62.5 — explicitly requested despite the two confirmed hangs above, not new information (superseded by the latency pass below)
After the SF10 and SF12 hangs above, the user asked to "max out the range." Was told directly, before implementing anything: both SF10 and SF12 (at BW125) have already hung the receiver, the SD-card SPI fix above is unrelated and doesn't change that risk, and lower-risk alternatives exist (lower bandwidth alone at SF7, or lower bandwidth + a small step like SF8). **The user explicitly chose SF12 + a halved bandwidth (62.5 kHz) anyway** — the single most aggressive available combination, stacking the exact spreading factor already confirmed to hang the receiver on top of an even more extreme symbol-duration/LDRO regime than the original SF12/BW125 attempt.
**What shipped at the time**: `radio.begin()` bandwidth `125.0 → 62.5`, spreading factor `7 → 12`, on both sender and receiver. Time-on-air for the 81-byte packet: symbol duration = 2^12/62500 ≈ 65.5ms (LDRO auto-enabled) → preamble ≈ 803ms + payload ≈ 93 symbols × 65.5ms ≈ 6095ms ≈ **6.9 seconds per transmission**. `LORA_TX_INTERVAL_MS` set to 9000ms for headroom.
**It worked (no hang) — but ~6.9s per packet made the dashboard feel unusably slow ("takes wayyy too long to reach the receiver"), which led directly to the latency-priority rule immediately below.** Whether it would have hung is now moot; it's been superseded before any further testing.

### Latency now prioritized over range — SF7 + BW500, explicitly requested, range cost accepted
Direct follow-up request after the SF12+BW62.5 config above turned out to work but be far too slow: get latency "as close to zero as possible even if that means shorter range," done immediately with no back-and-forth (the user was stepping away). Three levers, safest first:
1. **Coding rate** — already 4/5 (fastest available); no change.
2. **Spreading factor → SF7** — the lowest value already *proven* safe on this exact hardware. Deliberately NOT lower (SF6/SF5 are untested territory this project has never tried) — not worth gambling on with nobody available to debug a fresh hang.
3. **Bandwidth → 500 kHz** (was 125) — the actual, explicitly-authorized range-for-latency trade. Higher bandwidth means a much shorter symbol duration and far less airtime, at the direct cost of receiver sensitivity/link budget (roughly -12dB versus 125kHz — a real, substantial range reduction, not cosmetic).
**Time-on-air at SF7/BW500 for the 81-byte packet**: symbol duration = 2^7/500000 = 0.256ms (far under the 16ms LDRO threshold — no LDRO). Preamble ≈ (8+4.25)×0.256ms ≈ 3.1ms. Payload ≈ 128 symbols × 0.256ms ≈ 32.8ms. **Total ≈ 36ms per transmission** — about 190x faster than the SF12/BW62.5 attempt's ~6.9s, and even faster than the original SF7/BW125 baseline's ~144ms (the much shorter symbol time at BW500 wins out despite otherwise-identical settings).
`LORA_TX_INTERVAL_MS` dropped back to 200ms (real headroom above ~36ms) — matching `SENSOR_INTERVAL_MS`/`ESPNOW_TX_INTERVAL_MS` again, so LoRa updates as fast as the sensors themselves sample, not gated by radio airtime at all anymore.
**Range is now genuinely reduced from every prior configuration in this file's history** (125kHz was already the baseline; 500kHz is a real, substantial cut below that) — this was the explicit, accepted tradeoff, not an oversight. If range complaints resurface, the fix is dropping bandwidth back down (500→250→125), NOT raising spreading factor — SF10/SF12 are still confirmed-hung territory on this board, unrelated to anything in this latency pass.
**Not yet re-confirmed end-to-end on real hardware** as of this exact config (SF12+BW62.5 above was tested; SF7+BW500 has not).

### ADS1115 gain is switched per-read — don't assume a fixed gain
`readDividerVoltage()` sets `GAIN_TWOTHIRDS` (±6.144V FSR) before reading A0/A1; `readCurrentAmps()` sets `GAIN_ONE` (±4.096V FSR) before the A2-A3 differential read. These are deliberately different — the divider channels need the wider range to avoid clipping near 5V, the current channel wants the extra resolution. If you add a new ADS1115 channel, set its own gain explicitly rather than assuming the previous read's gain is still active.

### Current sensing is differential, not single-ended
`readCurrentAmps()` uses `ads.readADC_Differential_2_3()` (Vout − Vref) instead of a fixed `CURRENT_ZERO_V` constant like the old design did. This is intentional — the sensor's Vref pin is wired to A3 specifically so the true zero point is measured every sample instead of assumed. Don't reintroduce a hardcoded zero-offset constant; only `CURRENT_SENS` (V per A) needs calibration.

### Calibration constants that still need real numbers
- `CURRENT_SENS` (V/A for the YHDC HSTS016L) — still a placeholder pending bench calibration against a known load, don't treat it as verified.
- `VDIV_RATIO_MOTOR = 0.19893`, `VDIV_RATIO_BATT = 0.19954` — **calibrated against a multimeter**, no longer the nominal `1/5`. Motor: sketch read 12.97V vs multimeter 13.04V. Battery: sketch read 13.02V vs multimeter 13.05V. Re-run the procedure below if the resistors are ever swapped or the divider circuits rebuilt.

### Voltage divider calibration procedure
With the sketch running and printing `Motor Volt`/`Batt Volt` to serial:
1. Measure the true voltage at that divider's input node with a multimeter, at the same time the serial dump shows a reading.
2. Compute the corrected ratio: `new_ratio = old_ratio * (sketch_reading / multimeter_reading)`.
   - Example: divider reports 24.60V, multimeter reads 24.35V, old ratio is `1/5` (0.2) → `new_ratio = 0.2 * (24.60/24.35) = 0.2021`.
3. Put that value into `VDIV_RATIO_MOTOR` or `VDIV_RATIO_BATT` (whichever channel you measured) and re-flash.
4. Re-check against the multimeter — one pass is normally enough since the relationship is linear, but repeat if the source voltage was unstable during the first measurement.

Do this once per divider (motor and battery separately) — don't assume one calibrated value applies to both.

### Temp probe is a DS18B20, not analog — don't re-add ADC/NTC code here
Early in the V2 rework this was built as an analog NTC thermistor circuit (divider math, Beta equation, ADC oversampling/calibration) because the sensor was initially described as an "analog output" probe. It's actually a **DS18B20**, a digital 1-Wire sensor — none of that analog machinery applies, and it was the actual cause of the wild/inverted readings seen at the time (a 1-Wire digital pulse train read through an ADC as if it were a steady analog voltage produces meaningless numbers). The sketch now uses `OneWire`/`DallasTemperature` on GPIO6, same as V1 used on GPIO45. If temp readings ever look wrong again, don't reach for divider/thermistor math — check the 4.7kΩ pull-up and the data-line wiring first, and check `tempSensor.getDeviceCount()` in the boot log (0 means the sensor didn't respond).
- 9-bit resolution is set intentionally (`tempSensor.setResolution(9)`) to keep the blocking `requestTemperatures()` call (~94 ms) well under the sketch's 200 ms sensor-poll cadence — 12-bit default (~750 ms) would stall the loop.
- `readTempF()` returns `NAN` on `DEVICE_DISCONNECTED_C` rather than a bogus number — the print block checks `isnan()` and prints a clear DISCONNECTED line instead of a fake temperature.

### GPIO45 is not usable for analog input
This was a real wiring mistake caught early in the V2 rework, before the sensor was correctly identified as the digital DS18B20 above: GPIO45/46 on the ESP32-S3 are dedicated strapping pins with no ADC channel. Kept here as a standing rule for any *future* analog sensor — don't route one to GPIO45 or 46.

### RPM sensing — polarity-agnostic, period-based (V2.2 rework)
The original ISR design assumed the sensors idled LOW and pulsed HIGH (`RISING` + `INPUT_PULLDOWN`) — wrong for these unbranded modules, so it read zero. It was also wired to the wrong pins entirely (GPIO47/48, never connected — the sensors actually landed on **GPIO4 (motor) / GPIO3 (wheel)**; confirmed working via `rpm_pin_test.ino`). Once wiring was fixed, RPM values only moved in large fixed steps (~60 RPM per detected edge) because the first rework counted edges in a fixed 500 ms window — coarse by construction at low pulse rates.

The current version instead measures the **time between pulses** and converts that period directly to RPM, giving a smooth continuous value that updates on every single pulse instead of once per window:

- Edges are still detected with `CHANGE` (polarity-agnostic — works whether the sensor idles HIGH or LOW). Since one beam-block event produces two edges, only every *other* debounced edge (tracked via `motorParity`/`wheelParity`) is treated as a pulse boundary; the time between two such boundaries is a genuine full-pulse period regardless of which physical direction is rising vs. falling.
- `RPM_PIN_MODE` defaults to `INPUT_PULLUP` (idle HIGH) — the most common behavior for these break-beam modules. If a sensor's output floats or reads inverted, this is the first thing to try changing.
- If RPM reads exactly double the real value (verify by spinning a disc by hand and counting), flip `RPM_COUNT_BOTH_EDGES` to `0` and pick a single edge via `RPM_SINGLE_EDGE_MODE` — each detected edge then directly marks a pulse boundary.
- `RPM_STALE_MS` (1000 ms default) reports 0 RPM once a channel has gone that long without a new pulse, instead of freezing on the last computed speed when the disc actually stops.
- `RPM_DEBOUNCE_US` (1.5 ms default) is an electrical-noise floor only, not meant to filter real slot pulses — shrink it if RPM looks capped at very high speed.
- The serial dump still prints raw edge counts *and* live `digitalRead()` pin state every cycle for wiring diagnosis: edges always 0 with a pin state that never changes means a wiring/power problem, not a code problem — check sensor VCC/GND and the actual signal wire before touching the sketch. `rpm_pin_test.ino` (same folder) is a minimal standalone sketch for exactly this check, independent of the interrupt/RPM logic.

### Boot sequence order matters
VEXT power rail is enabled and given time to stabilize *before* I2C init — keep that order; IMU/ADS1115 detection depends on the rail being up first.

### Code style
- `pollGps()` runs every `loop()` iteration to keep the UART buffer drained; heavier work (`updateSensors`, serial dump) is gated behind `SENSOR_INTERVAL_MS`. Keep that split.
- Keep the ASCII banner section headers (`════...`) — used throughout both `.ino` and `.h` files in this repo for visual navigation.

### SD card logging — own SPI bus, pins chosen after two real pin-conflict misses (and a THIRD conflict at the peripheral-host level, not the pin level)
`SD_CS_PIN`/`SD_SCK_PIN`/`SD_MOSI_PIN`/`SD_MISO_PIN` (47/48/7/5) run on a **separate** `SPIClass sdSPI(HSPI)` instance, not the default `SPI` object the LoRa radio already uses — the radio's SPI pins (SCK=9/MISO=11/MOSI=10) are wired chip-to-chip internally to the co-packaged SX1262 and were never broken out to a header pin at all, so sharing that bus from an external module isn't physically possible, only a second independent bus is. **These four pins were picked from the real Heltec V4-R2 pinout diagram, not assumed** — an earlier pass twice recommended pins that turned out to already be taken (GPIO9/10/11, actually the LoRa radio's internal-only pins with nothing to share; then GPIO6, actually the temp probe's pin) before landing on this set, cross-checked against every pin already in this file's own Hardware table plus the LoRa radio's internal pins. **If any future pin is ever added to this board, check it against the FULL current Hardware table above first** — a pin recommendation reasoned from a generic Heltec datasheet/pinout without that cross-check is exactly how the two earlier misses happened.

### ⚠️ REAL, CONFIRMED bug: `sdSPI` was originally `SPIClass(FSPI)` — same underlying peripheral as the default `SPI` object LoRa uses, NOT a separate bus, despite using different pins
Different GPIO pins do **not** mean different hardware on the ESP32-S3 — arduino-esp32's own default global `SPI` object (the one `SPI.begin(LORA_SCK, ...)` uses for the LoRa radio) is itself internally `SPIClass SPI(FSPI)`. A second `SPIClass sdSPI(FSPI)` for the SD card wraps the exact same SPI2_HOST peripheral, and since ESP32 SPI peripherals route their pins through an internal GPIO matrix, `sdSPI.begin(SD_SCK_PIN, ...)` — called in `setup()` *after* the LoRa radio's own init — silently reprogrammed that shared peripheral's pin routing to the SD card's pins, out from under the radio.
**Symptom on real hardware, confirmed via a live user report ("hit yes on the agent, it doesn't forward") traced all the way back to this**: `radio.begin()` (runs first, before SD init) kept reporting success, but every single subsequent `radio.startTransmit()` call in `loop()` (which only runs after `initSdCard()` has already hijacked the shared peripheral) failed with a generic RadioLib error code — confirmed via a raw serial sniff of the sender showing `[LoRa] startTransmit() ERR -1` on literally every transmit attempt, at SF7 (the original, previously-known-working setting), ruling out the spreading-factor investigations elsewhere in this file as the cause. This had been a **latent** bug since the SD card feature was first added — it needed both features actually exercised together end-to-end (SD logging AND a receiver actually listening for real packets) to surface, which hadn't happened until this pass.
**Fixed by moving the SD card onto `HSPI` (SPI3_HOST) instead of `FSPI`** — the ESP32-S3's other general-purpose SPI peripheral, genuinely independent hardware from FSPI, not just a different pin assignment on the same one. **The general lesson, not just for this specific bug**: on ESP32-S3, "give it its own `SPIClass` instance on different pins" is NOT sufficient to guarantee an independent bus — check which peripheral HOST (`FSPI`/SPI2 vs `HSPI`/SPI3) is actually requested, and confirm it doesn't match whatever the default `SPI` object (or any other explicitly-hosted `SPIClass`) is already using, regardless of pin numbers.
`initSdCard()` (called once in `setup()`, after the LoRa radio) scans for the first unused `/LOGnnn.CSV` filename (001-999) rather than assuming one's free — the card persists across power cycles, so a fresh boot needs to find where the last run left off. One new file per power-cycle, not one always-appended file, mirroring `telemetry_web`'s own session-boundary reasoning for the same underlying problem (keep runs separable for post-race analysis) server-side.
`logToSD()` (called once per `SENSOR_INTERVAL_MS` tick, right after `updateSensors()`, independent of `LORA_TX_INTERVAL_MS`/`ESPNOW_TX_INTERVAL_MS`) writes the exact same `pkt` LoRa/ESP-NOW would send — the SD log and the transmitted telemetry can never disagree, since both read the same struct. **Flushed on every single write, not batched** — deliberate: the whole point of a local backup is surviving a sudden power loss (a real, plausible failure mode for a race vehicle), and data sitting in an unflushed buffer when power actually cuts is exactly the data this log exists to protect against losing. At 5Hz this is a small enough write volume that the extra flush overhead doesn't matter.
Missing/failed SD card is non-fatal — `initSdCard()` warns and leaves `sdReady` false; `logToSD()` just returns immediately every tick after that. LoRa, ESP-NOW, and every sensor keep working exactly as before regardless of whether a card is even inserted.
**LoRa TX itself is now believed fixed (this pass) but not yet re-confirmed end-to-end on real hardware** — the SPI-conflict fix above directly explains the observed symptom and is a real, well-reasoned root cause, not a guess, but hasn't yet been re-tested with a full sender→receiver→agent→dashboard round trip since the fix. SD card logging itself (separate from the LoRa-conflict bug) is still also unconfirmed on real hardware — same caveat as before, confirm the card mounts (`[OK] SD card logging active`) and produces real CSV rows.

### RTC (Elegoo DS1307-V03) — second I2C bus, NOT the shared IMU/ADS1115 bus
The DS1307 has a **fixed, non-configurable I2C address (0x68)** — the same address the existing MPU6050-compatible IMU already answers to on the shared `Wire` bus (GPIO17/18). Putting the RTC on that same bus means one of the two devices silently doesn't respond; the fix is a genuinely separate I2C bus, not a shared one.

The ESP32-S3 has two independent hardware I2C controllers, and (unlike, say, the LoRa radio's SPI pins, which are wired chip-to-chip and never broken out to a header) the I2C peripheral is routed through the chip's internal GPIO matrix, so it isn't tied to any particular "I2C" silkscreen pins — this is exactly why the *existing* bus already lives on GPIO17/18 rather than some fixed default pair. The RTC's second bus uses `TwoWire rtcWire(1)` on **GPIO1 (SDA) / GPIO2 (SCL)** — cross-checked against the full current pin list in the Hardware table above (same discipline as the SD-card pin selection two rules up) before being chosen; both were confirmed clean.

- `initRtc()` (called once in `setup()`, before `initSdCard()` so the very first log rows already have a real timestamp) calls `rtc.begin(&rtcWire)`; if the DS1307 never ran before (first power-up, or a dead CR1220 backup battery), `rtc.isrunning()` is false and the code sets it once from the sketch's own compile time (`__DATE__`/`__TIME__`) — after that the DS1307's own backup battery should keep it running across power-cycles without needing this again.
- `getRtcTimestamp()` writes `"NO_RTC"` into the SD log's timestamp column instead of a blank/garbage value if the RTC was never detected — keeps the CSV's column count consistent either way rather than shifting columns when the RTC is absent.
- Missing/dead RTC is non-fatal, same pattern as the SD card and every other optional peripheral in this sketch — `rtcReady` stays false, the SD log just gets `"NO_RTC"` in that column, nothing else is affected (the RTC never touches the LoRa/ESP-NOW packet, only the local SD log).
- Requires the **RTClib** library (Adafruit) — not built into the ESP32 core, unlike `SD`.
- **Not yet verified on real hardware** — same caveat as the SF10 and SD-card rules above; wired and coded but not bench-tested as of this pass.

### `epoch_time` — the RTC timestamp is now also sent over LoRa, as a raw 4-byte int
`telemetry_packet_t.epoch_time` (`uint32_t`, Unix seconds, `0` if the RTC was never detected) is populated once per `updateSensors()` tick from `rtc.now().unixtime()` and rides in the same LoRa packet as everything else — added to `config.h` (both copies, kept in sync as always — see the rule above).
**Deliberately sent as a raw integer, not a formatted date string** — this was a direct ask to keep the added latency as low as possible: 4 extra bytes on the wire is a small, fixed addition to the packet regardless of spreading factor, versus a `"YYYY-MM-DD HH:MM:SS"` string (19+ bytes) which would meaningfully add to each transmission's time-on-air, especially at SF10 where airtime is already the whole reason for the ~2s TX interval. All date/time *formatting* (the actual human-readable string) happens off the radio link entirely — on the SD card locally (`getRtcTimestamp()`, unchanged, still a local-only column) and on `greenpower_receiver`'s side once the packet has already arrived (see that project's own CLAUDE.md) — so the LoRa link only ever carries the smallest representation that still has full date+time+seconds resolution.
Same non-fatal pattern as everywhere else the RTC is used: `epoch_time` is simply `0` if `rtcReady` is false: nothing downstream should treat `0` as a real 1970-01-01 timestamp — it means "no RTC."

### Packet shrink — `hdop`/`esc_mode`/`esc_state` compacted to cut LoRa airtime further
Follow-up to the `epoch_time` addition above: once the packet had grown to 98 bytes, a direct ask to trim airtime further as much as reasonably possible without a full fixed-point rework of every field. Two low-risk, high-value changes, both purely a wire-format change — nothing about what data is collected or how it's used elsewhere in this sketch changed:
- **`hdop` (was `float`, 4 bytes) → `hdop_x10` (`uint8_t`, 1 byte)** — HDOP × 10, giving 0.1 resolution up to HDOP 25.4, which is already far past the point a GPS fix is usable for anything. `PKT_HDOP_NO_FIX` (255) replaces the old `99.9f` "no fix" placeholder, which no longer fits in a byte. `packHdop()` (in `updateGps()`) does the float→byte conversion, clamped to 0-254 rather than overflowing on an unexpectedly large value.
- **`esc_mode`/`esc_state` (were `char[8]` each, 16 bytes total) → `esc_mode_code`/`esc_state_code` (`uint8_t` each, 2 bytes total)** — these only ever hold one of a handful of known values (`"ECO"/"NORMAL"/"SPORT"`, `"IDLE"/"REENG"/"RAMP"/"HOLD"`), so an 8-byte ASCII string per field was pure waste on the wire. `PKT_ESC_MODE_*`/`PKT_ESC_STATE_*` in `config.h` define the codes (must match `../esc%20controller/throttle_controller.ino`'s `modeName()`/`stateName()` exactly); `escModeToCode()`/`escStateToCode()` (this file) convert the real strings parsed off the ESC UART line into codes only at the point they're copied into `pkt` — every *other* consumer in this sketch (SD log via `logToSD()`, ESP-NOW via `espNowSend()`, the serial debug dump) still uses the real strings straight from the `esc` struct, not the packet's codes, since only the LoRa wire format needed shrinking, not the sketch's own internal data.

**Packet is now 81 bytes** (down from 98, and originally 94 before `epoch_time`). Recomputed via the same Semtech time-on-air formula already used elsewhere in this file: ~985ms → **~862ms per transmission at SF10** (~12% less airtime), without touching spreading factor, TX interval, or anything about the async-TX machinery. A more aggressive fixed-point rework of the remaining ~18 float fields was considered (could reach ~54 bytes, ~617ms, ~37% less airtime) but deliberately not done in this pass — explicitly deferred as a bigger, riskier change (every field needs its own scale factor chosen carefully — e.g. `yaw_deg` drifts past ±180° over a run and can't just be squeezed into a naive fixed range) that isn't worth stacking on top of SF10/RTC/SD, all still unverified on real hardware.
**Not yet verified on real hardware** — same caveat as everything else added this pass.

- **Explicit follow-up request: "is there no way you can actually measure the lora time on air"** — every airtime figure up to this point (this file's own comments, the dashboard's old `computeLoraAirtimeMs()`) was a computed Semtech-formula estimate, never a real hardware measurement. Answer: yes, and it's now implemented. Given the choice between "verify the estimate once via serial" (free) and "stream the real measured value to the dashboard live" (costs ~2 bytes/packet), the user chose to stream it live.
- **`loraTxStartUs`** is stamped with `micros()` immediately before `radio.startTransmit()` in `loRaTx()` — deliberately AFTER any setup work that call itself does internally, not before, so that SPI handoff time isn't counted as "airtime." **`loraTxDoneUs`** is stamped with `micros()` INSIDE `setLoraTxFlag()` itself (the `IRAM_ATTR` ISR RadioLib calls via `setPacketSentAction()`) — not later when `checkLoraTxComplete()` gets around to polling the flag in `loop()`. This matters: stamping in the ISR means the measurement's only real error source is genuine hardware/ISR-entry latency (microseconds), not loop() polling granularity — this is real hardware timing, about as good as an oscilloscope on the antenna line, not a software approximation.
- **The measured duration for a transmission is written into `pkt.airtime_ms_x10` in `checkLoraTxComplete()`, AFTER that same transmission has already left the radio** — there's no way to retroactively stuff a measurement into bytes already transmitted. So every packet's `airtime_ms_x10` field reports how long the PREVIOUS transmission actually took, one 200ms cycle of lag. At steady 5Hz this is invisible in practice (SF/BW/packet size never change mid-run, so the real value is nearly constant packet to packet) but is documented explicitly in three places (this field's own struct comment in `config.h`, the `checkLoraTxComplete()` comment, and here) since it's the one place this feature's real behavior doesn't match "what it sounds like it should do."
- **Packet grew 42 → 44 bytes** (2-byte `uint16_t airtime_ms_x10`, scale `PKT_SCALE_AIRTIME=10.0f`, same clamp-and-round `pktEncU16()` helper every other scaled field uses) — recomputed time-on-air ≈ **21.3ms** (was ~20.0ms at 42 bytes). A deliberate, small, explicitly-requested regression against last session's compression work, not an oversight — see that session's whole "compress the data" thread for why 42 bytes was reached in the first place.
- **The sender's own `[LoRa] TX OK` debug line now prints the measured value too** (`airtime=X.XXms (measured)`) — the ONE place in this codebase where the real number is visible without needing the dashboard/receiver at all, useful for a quick sanity check straight off the sender's own serial monitor.
- **`radio.implicitHeader(sizeof(telemetry_packet_t))`, not `sizeof(pkt)`, on both sender and receiver** — a real compile error caught this pass: the receiver's `pkt` is a LOCAL variable scoped inside its packet-handling function, not visible from `setup()` where `implicitHeader()` is called (`'pkt' was not declared in this scope`). Fixed on both sides for consistency (the sender's `pkt` happened to be global, so it wasn't hitting the same error, but `sizeof(telemetry_packet_t)` is correct regardless of a `pkt` variable's scope on either side, and the implicit-header length now automatically tracks the struct size on every future field change — no separate constant to keep in sync).
- **Not yet reflashed/verified on real hardware.**

## Current State (V4.3 — implicit header + trimmed preamble: ~20ms airtime, near the SF7/BW500 floor)

- **Explicit request to push transfer speed as far as possible** on top of V4.2's compression. Two more RF-level (not payload-level) cuts, both free — no range or data cost:
  - **Implicit header mode** (`radio.implicitHeader(sizeof(pkt))`, called right after `radio.begin()` succeeds) — a LoRa explicit header normally carries the payload length + coding rate in-band so a receiver that doesn't already know them can figure them out; this project's receiver always does (same `telemetry_packet_t` from the same shared `config.h`), so that header is pure overhead here. Saves ~1.3ms/packet. **The receiver's own `radio.begin()` block MUST call `radio.implicitHeader(sizeof(pkt))` too, with the same length, or packets stop decoding entirely** — this is now a hard sender/receiver coupling, not just a nice-to-have match.
  - **Preamble trimmed 8 → 6 symbols** (`LORA_PREAMBLE_SYMBOLS` in `config.h`, shared by both sides) — 6 is Semtech's documented floor for reliable SX126x sync, not an arbitrary smaller number. Saves ~0.5ms/packet. Slightly increases the (already small) chance of an individual packet's sync word being missed in a noisy RF environment — acceptable for a stream that free-runs at 5Hz and self-heals on the very next transmission, not something worth doing for a one-shot or ack'd protocol.
- **Combined new time-on-air ≈ 20ms/packet** (down from ~21.8ms after V4.2 alone, ~36ms right after the original SF7/BW500 pivot, ~6.9s at the SF12/BW62.5 range attempt).
- **This is close to the practical floor for SF7/BW500 with this packet.** Two further cuts were considered and deliberately NOT applied without asking first:
  - **Dropping `epoch_time` (4 bytes) would buy another ~1.3ms** but removes the sender's own RTC-stamped absolute timestamp from the wire entirely (the dashboard would fall back to server-receive-time only, which given ~20ms airtime is a negligible skew, but is still a real feature loss, not just a precision loss).
  - **Going below SF7 (SF6/SF5)** was explicitly flagged as untested territory this project has avoided — see the ⚠️ rules above about SF10/SF12 hangs — and CRC removal was checked and turned out to save *zero* additional symbols at this exact packet size anyway (the ceiling-division math already lands on the same boundary), so it wasn't worth the integrity trade-off for no benefit.
- **Not yet reflashed/verified on real hardware** — and this one has a real new failure mode to watch for on first test: if the sender's and receiver's `LORA_PREAMBLE_SYMBOLS`/implicit-header length ever drift apart (e.g. one side edited without the other), packets will silently fail to decode rather than just underperform — worth an explicit first-boot check that packets are actually arriving, not just that both radios report `[OK]`.

## Current State (V4.2 — packet compressed to 42 bytes: fixed-point instead of float)

- **The fixed-point rework flagged as "deferred" in V-1's entry below (73→~54 bytes) was actually done, and went further — 73 → 42 bytes.** Explicit request ("compress the data to as little as possible so it transmits super fast"). Every float field except `latitude`/`longitude` (kept float — position precision genuinely needs it) is now a scaled `int16`/`uint16`, and the three `esc_*_pct` fields are now whole-percent `uint8` instead of float. Scale factors, the sentinel for "no reading" (`PKT_TEMP_NO_READING`, replacing the old `isnan(float)` check — an int16 has no NaN), and the `pktEncU16()`/`pktEncI16()`/`pktEncPct()` clamp-and-round encode helpers all live in `config.h`'s "Fixed-point compression" block — see that file for the exact resolution/range chosen per field (all deliberately far beyond what this car's sensors can actually produce, e.g. ±327.67 A current range, 0.01°C... none of these are tight fits).
- **Recomputed time-on-air at SF7/BW500: ~36ms → ~22ms per packet** (128 payload symbols → 79) — a further ~40% airtime cut, and unlike the SF7/BW500 pivot this one costs nothing in range at all; it's pure payload-size reduction, not an RF-parameter trade-off. See the dedicated comment above `LORA_TX_INTERVAL_MS`.
- **Every place that used to read a `pkt.*` float field directly (SD log, serial debug dump, the ESP-NOW CSV payload to `steering_wheel_display`) now decodes it back to a human float first** (`pkt.field_x10 / PKT_SCALE_X`) — those wire formats (the SD CSV columns, the ESP-NOW `speed,batV,rpm,amps,...` line) are themselves **unchanged**; only `telemetry_packet_t`'s own internal storage got smaller. `greenpower_receiver.ino`'s pretty-dump/JSON block does the same decode — see that folder's own Current State entry. This is the same kind of cross-folder-but-not-obviously-so change the repo root `CLAUDE.md` calls out for `telemetry_packet_t`; both `config.h` copies moved together.
- **`telemetry_web` needs no changes for this** — the receiver's JSON output (what `receiver_agent` actually forwards) still uses the same keys and real human units (mph, volts, °F, ...) as before; the fixed-point encoding is entirely invisible past the receiver's own decode step.
- **Not yet reflashed/verified on real hardware.**

The SF12+BW62.5 range attempt below worked (no hang) but had ~6.9s airtime, which felt unusably slow — this pass trades range for speed instead: SF7 (proven safe, not a new gamble) + BW500 (the real range-for-latency cost). - **SF12 + BW62.5 (the prior range attempt, now superseded) DID work without hanging** — a real, useful data point: SF12 alone (at BW125) hung the receiver twice before, but SF12+BW62.5 did not. Worth remembering if range is ever revisited — the earlier "SF12 always hangs this board" conclusion wasn't quite the whole story.
- **Found and fixed a real, SEPARATE bug that fully explained "the receiver never gets anything, even at SF7"**: `sdSPI` was `SPIClass(FSPI)`, the SAME underlying peripheral (SPI2_HOST) that arduino-esp32's default `SPI` object (used by the LoRa radio) also uses internally — different pins, but NOT different hardware. `initSdCard()` running after LoRa init silently reprogrammed the shared peripheral's GPIO-matrix routing to the SD card's pins, so `radio.begin()` succeeded (ran first) but every later `radio.startTransmit()` failed (ran after the hijack). Confirmed via a live serial sniff showing `[LoRa] startTransmit() ERR -1` on every attempt, at SF7. Fixed by moving `sdSPI` to `HSPI` (SPI3_HOST) — genuinely independent hardware. See the dedicated ⚠️ rule above.
